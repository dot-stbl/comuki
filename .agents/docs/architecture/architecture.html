Comuki

Comuki — платформа, где умный «мозг» декомпозирует задачи и управляет роем дешёвых эфемерных агентов, которые пишут, тестируют и выкатывают фичи в контейнерах — с общей базой знаний, правилами на лету и помощью локальному Claude Code.

Статус: до реализации Фаза: MVP — человек в петле Сервисов в v1: 2–3 Мозг: ведущая модель Воркеры: рабочая модель

01Принципы

Вся система держится на нескольких решениях. Если их нарушить, она перестаёт работать — поэтому их стоит зафиксировать до кода.

P1

Агенты — stateless, состояние живёт в мозге. Каждый агент это чистая функция: (бриф + снапшот кода) → (дифф + отчёт + статус). Никакой памяти между запусками. Весь durable-слой — DAG задач, журнал, знания, состояние кода — снаружи агента. Тогда любой агент перезапускается без последствий.

P2

Мозг думает, но не является позвоночником. ведущая модель принимает решения — план, бриф, вердикт, ремонт — но источник правды и управляющий цикл живут в детерминированном коде, а не в контексте сессии. «LLM предлагает — система распоряжается».

P3

Контекст не наследуется, а собирается. Качество выхлопа агента ≈ качеству брифа. Контекст-менеджер выдаёт минимально достаточный срез: карта репозитория, релевантные файлы, конвенции, дайджест предыдущих шагов.

P4

Верификация — детерминированная в первую очередь. Сначала объективные проверки (компиляция, тесты, типы, линт), и только потом LLM-ревью. Гейт нельзя строить на вопросе модели «ты всё сделал правильно?». Чем жёстче этот гейт, тем надёжнее держится дешёвая модель — драконовские анализаторы (Roslyn, warnings-as-errors), которые физически не дают собрать кривой код, это несущая опора качества, а не придирка. Ослабить их «чтобы быстрее собиралось» = тихо выбить главную опору.

P5

Всё — событие в append-only журнале. Это даёт дебаг, реплей и материал для дайджестов контекста. Журнал — «чёрный ящик» системы.

P6

Эфемерность — это фича. Контейнер отработал и снесён; свежий контекст на каждую задачу убивает деградацию длинных сессий. Единственное обязательное условие — извлечь результат до сноса.

P7

Управляющая плоскость — это код. Правила, скиллы, агенты, брифы версионируются как код: правятся через дебаг → ревью → эвал-харнес → новая версия. Их свод и версия SDK берутся по зафиксированному реферу, который пинится на прогон. Человек всегда замыкает петлю — авто-самоизменения нет.

02Карта сервисов

Внешне это «много коробок», но если заметить, что часть из них — не сервисы, остаётся 2–3 вещи, которые реально надо написать. Мозг — это вызов ведущей модели по API изнутри оркестратора. Dashboard — read-only вьюха поверх БД. Секреты — готовый Vault. Оба потребителя (автономные воркеры и локальный Claude Code разработчиков) подключаются через единый MCP-шлюз.

Что реально пишется:

  • Оркестратор. Control plane: машина состояний DAG, расписание, конкурентность, ретраи, диспетчинг контейнеров, вызовы мозга. Владеет журналом и источником правды.
  • MCP-сервер знаний и правил. Вектор-база, движок правил, retrieval. Единая поверхность для автономных воркеров и локального Claude Code.
  • Сервис ключей (опционально). Если не берёшь managed-vault — выдача, ротация, скоупы и атрибуция стоимости по продукту/агенту.

03Управляющий цикл

Опус планирует и собирает бриф, контейнер с агентом выполняет, верификатор проверяет. Зелёный — мердж и разблокировка зависимых задач; красный — бриф пересобирается с ошибкой. Эта петля «не прошло → новый бриф» — основной механизм качества, а не аварийный режим: дешёвые модели чаще выдают красный, а не падают.

Контейнер — это скот, а не питомец, но результат надо вытащить до сноса. «Готово» для агента = закоммитил в свою git-ветку (worktree) И отдал структурированный отчёт. Диспетчер соблюдает порядок: запустил → дождался результата → сохранил → снёс.

04Модели: ведущая и рабочая

Архитектура оперирует не вендорами, а двумя ролями: ведущая модель за «мозгом» (план, контракт, ревью, ремонт) и рабочая модель за стадийными воркерами. Какая физическая модель стоит за ролью — это маппинг в проксе, а не часть архитектуры. Сейчас за ролями: ведущая — Opus, рабочая — GLM (z.ai) и MiniMax; все они отдают Anthropic-совместимый эндпоинт, поэтому обвязка остаётся одна — Claude Code / Agent SDK для всех.

Раз рабочая модель слабее ведущей, качество держится на брифе (его пишет ведущая) и на гейте верификации. Рабочей модели дают меньше свободы: жёсткий allowedTools, ригидный контракт вывода, мелкая нарезка задач. Ведущую держат и как ремонтную бригаду — после N провалов задача эскалируется на её проход, а не крутится бесконечно на дешёвых ретраях.

Модельный прокси

Контейнер знает только ANTHROPIC_BASE_URL и ANTHROPIC_AUTH_TOKEN — поэтому ему подсовывают виртуальный URL (смотрит на прокси) и виртуальный ключ, который понимает только прокси. По этому ключу прокси резолвит физического провайдера, реальный ключ, модель, бюджет и скоуп — подменяет url+ключ и форвардит на настоящую апишку. Контейнер полностью провайдер-агностичен: он не знает, какую физическую модель за ролью дёрнул прокси. Перевести workflow с одной модели на другую — это поменять маппинг ключа в прокси, контейнер не трогаем. Так маршрутизация моделей переезжает на сервер и становится одной таблицей, а не env, размазанным по контейнерам.

Протокол на обоих концах один — Anthropic Messages внутрь, Anthropic-совместимый наружу, — поэтому в типовом случае прокси не транслирует, а пробрасывает поток, подменив url+ключ. Это и позволяет держать его тонким, что важно: через него идёт каждый вызов и людей, и роя. Тот же прокси обслуживает локальный Claude Code разработчика — со своим виртуальным ключом, идентичностью, бюджетом и приоритетом, — и тогда правило «люди > рой» становится принуждаемым.

05Знания и правила

Код и документацию разделяем. Код в RAG не индексируем — агент грепает прямо в worktree (нативная сила Claude Code; RAG по коду быстро устаревает). А документацию, спеки, прошлые решения и правила кладём в retrieval-стор и отдаём через MCP. Мозг при этом ничего не хранит — просто ищет в вектор-базе по MCP.

Документирование — последняя стадия пайплайна, которую дёргает событие: фича дошла до прода → оркестратор ставит doc-задачу дешёвому агенту, у которого весь вход уже есть (дифф, бриф, тесты). База обновляется сама.

Правила делим на мягкие и жёсткие. Мягкие (конвенции, стиль) идут в бриф/CLAUDE.md — это контекст. Жёсткие (запреты) принуждаются хуками, которые перехватывают поведение агента в ключевых точках, плюс гейтом верификации. Правила версионируем и скоупим: глобальные / на продукт / на тип задачи. «На лету» означает, что оркестратор читает правила из стора в момент сборки брифа, а не на деплое.

06Workflow на примере

Два приложения — Магазин (витрина) и Админка (внутренняя панель). Прилетает тикет: «добавить избранное в Магазин». Сначала изучатор в режиме read-only исследует код и базу знаний и спрашивает мозг «такого ещё нет?» — чтобы не плодить дубль: если фича уже есть, тикет коротко замыкается, если частично — план расширяет существующее. Дальше планировщик декомпозирует задачу, и первым артефактом рождается не код, а контракт API (OpenAPI) — шов, по которому фронт и бек идут параллельно. Каждая стадия — отдельный контейнер-воркер со своим брифом, моделью и allowedTools.

DAG строится под задачу, а не разворачивается из шаблона. Граф стадий — подмножество из каталога известных типов (изучение, контракт, миграция, бек, фронт, тесты, деплой, доки), которое планировщик выбирает по фактам изучателя, а не по тексту тикета. Чисто фронтовая фича (изучатель подтвердил: данные уже приходят с бека) даёт короткий граф — фронт → тесты → деплой, без контракта, бека и миграции. Если «фронтовая» задача на деле требует нового эндпоинта — добавляется лейн бека. Состав и число воркеров — производная графа: меньше узлов → меньше воркеров. Ключевое: «фронт-онли» определяется фактами из кода (изучатель ходил двумя линзами), а не формулировкой — иначе граф выйдет неполным, фронт позеленеет на моках, интеграция сломётся. Поэтому состав графа — часть плана и валидируется как план (ведущая модель / человек), а планировщик не выдумывает новых типов стадий — собирает из каталога и расставляет зависимости.

Окружения по этапам

Изоляция от прода — по конструкции, а не по дисциплине. Каждая стадия получает одноразовое окружение, засеянное из схемы и конфига прода, но никогда из его данных и секретов. В лейне бека сначала миграция на эфемерной БД, затем ручки против неё; фронт параллельно собирается против mock-сервера, сгенерированного из контракта, а на синхронизации переключается на реальный backend; на стадии тестов всё поднимается вместе как preview-окружение на ветку. Прод касается только последняя стадия за гейтом — поэтому «сломать прод» невозможно по конструкции.

Агенты и правила против слопа

Воркеры используют pi (контроль, наблюдаемость), разрабы — форк GSD под Claude Code (интерактивный UX). Оба агента правил не хранят — получают извне. Жёсткие правила (запрет править тесты, пушить в main, прогон линт/типов) принуждаются механикой каждого агента: pi-расширения у воркеров, Claude Code hooks у разрабов — маленький фиксированный набор, реализуется дважды. Мягкие правила и скиллы — единый текст, оба читают одинаково. Два свода по природе: проектные (в репе продукта, для всех) и воркер-правила (в dashboard, только рою).

Сильнейшее правило против слопа — дизайн-система в репозитории. Токены и компоненты как единственный источник, а правило «строй только из DS-компонентов и токенов» принуждаемо: линт/хук ловит сырые hex-цвета, отступы мимо токенов и не-DS-компоненты, плюс правило «нет компонента без story». Дизайн-система получается сразу и ограничителем генерации, и поверхностью визуальных тестов — это на порядок надёжнее, чем просить модель «быть консистентной».

И сильнее всего против слопа работает то, что система применяет проверенные рецепты, а не изобретает подходы. «Как создать рекламную кампанию», «как сделать пагинацию», «как сделать фильтрацию» — это скиллы Claude Code, которые вы пишете и обкатываете локально на обычном Claude Code до того, как доверить рою. Принцип: новый тип работы сначала становится проверенным скиллом, потом — доступным оркестратору. Агент идёт по заранее обкатанным рельсам, а не сочиняет с нуля — и те же скиллы становятся кандидатами в golden-задачи эвал-харнеса.

Внутренний цикл воркера

Агент-воркер (pi) гоняет внутри контейнера цикл одной задачи: изучение → план → сверка плана → исполнение. К comuki-mcp воркер обращается дважды и за разным. На входе — retrieval: «дай рецепты, правила и доки под эту задачу» (материал, не оценка). После плана — проверка фактов: «что из этого уже есть и не нарушает ли правил» — то есть MCP отвечает не «хорош ли план», а «уже ли».

Поэтому изучатор смотрит две линзы сразу: comuki-mcp знает задокументированные фичи (их пишет doc-агент), а сырое состояние кода — это агентный grep по worktree. Вместе они закрывают «уже сделано?»: «построено ли это как фича» — к MCP, «написана ли уже такая функция» — к grep; остаток ловят мердж и человек.

Качество плана агент не судит сам — самооценка дешёвой модели всегда «да». Техническую сторону ведёт ведущая модель, и в структурированном проекте это лёгкий проход «впиши в существующее по правилам», а не «придумай с нуля». На локальном Claude Code второй вопрос естественно становится человеком; у headless-воркера — уровнем Comuki.

Контейнер каждый раз чистый и тянет правила, скиллы и SDK свежими — поэтому версия управляющей плоскости пинится на прогон: при старте оркестратор резолвит ревизию (свод правил + версия агента) и пишет её в артефакт, а все контейнеры прогона берут именно её. Так прогон внутренне согласован — собран из одного свода, а не из «правил до правки» и «правил после». Правка вступает в силу со следующих запусков; перезапуск застрявшего — это новый прогон на новой ревизии, а не доигрывание старого с подменёнными правилами. Агенты и контент (правила/скиллы) версионируются раздельно — у них разный ритм изменений.

Debug-агент. Когда пайплайн застрял (N раз не проходит) или проблему увидели перед продом, человек запускает debug-агента: тот читает артефакты прогонов и ищет, чего не хватает в правиле, скилле или брифе. Это и есть «управляющая плоскость как код» в действии — дебаг → предложение правки → ревью человеком → прогон через эвал-харнес → новая версия → перезапуск и проверка. Менять и одобрять — человек; debug-агент лишь помогает найти причину.

Тест-фреймворк

Это гейт верификации, разложенный по слоям. Детерминированное (типы, линт, юнит, сборка) → визуальный слой по компонентам: каждый компонент рендерится изолированно в Storybook, скриншот-диф против baseline плюс проход vision-модели, которая смотрит на рендер и ловит кривую вёрстку (переполнения, разъезды, сломанный респонсив) — дешевле и точнее, чем гонять весь E2E → Playwright E2E по живому preview (агент сам пишет и гоняет сценарий «добавил в избранное → видно в списке»). Находки уходят структурно обратно на стадию frontend со скриншотами. Связка с рисками: раз агенты сами пишут тесты, тесты по умолчанию слабые, поэтому визуальный ревью и человеческие приёмочные тесты на критичных путях обязательны, а хук на запрет правки тестов закрывает читерство.

Таск-трекер

Трекер — это intake и поверхность статуса (Linear / Jira / Asana / monday). Тикет в состоянии «ready for agent» триггерит подхват. Поля мапятся в конфиг прогона: лейбл приложения → репозиторий/окружение/правила; критерии приёмки → спека верификации; приоритет → расписание. Оркестратор двигает тикет по статусам и комментит артефакты — PR, preview-URL, результаты тестов, стоимость. Человеческий аппрув на деплой — переход статуса, завязанный на очередь аппрувов в dashboard.

Два приложения почти ничего не усложняют: всё, что их разделяет, — лейбл на тикете и скоуп через всю модель данных (репо, окружения, правила, знания, бюджет, ключи у каждого свои). Это та самая мультиарендность из раздела рисков — её закладываем с первого дня.

07Dashboard

Три функции: ставить задачи, настраивать поведение системы и наблюдать за роем.

Постановка задач (intake). Вход системы в MVP — человек накидывает задачу прямо в дашборде (на старте — тестовые задачи на тестовых репозиториях), она падает в очередь оркестратора. Внешнего трекера (Jira/Linear) на старте нет — коннектор далёкое «потом»; intake живёт внутри Comuki. Продуктовое «что делать» — в постановке человеком; техсторону дальше ведёт ведущая модель.

08Проблемные места и риски

Здесь самое важное. Система автономная, нодетерминированная и с правом выката в прод — то есть права на ошибку у неё мало. Ниже — где она треснет и что с этим делать. Тег показывает остроту.

Управляющий цикл и состояние

Необратимые действия при падении оркестратора

критично

Если оркестратор упал между «выкатил в прод» и «записал, что выкатил», после рестарта он может выкатить повторно. Откатить прод нельзя.

Лечение: проектируй на at-least-once, а не exactly-once. Перед каждым необратимым шагом пиши намерение в журнал, после — исход, в одной транзакции с действием там, где возможно. Идемпотентные ключи на дисптач, мердж и деплой. Любой шаг должен уметь спросить «я это уже сделал?» прежде чем делать.

Утечка ключей через агента

критично

В контейнер с агентом, который выполняет сгенерированный LLM bash, инъектится API-ключ модели. Агент (или промпт-инъекция из репозитория/доков) может вывести ключ наружу.

Лечение: контейнер не видит настоящий ключ — ему дают виртуальный URL (на прокси) и виртуальный ключ, который понимает только прокси; реальные ключи провайдеров живут в секрет-менеджере, который прокси читает. Виртуальный ключ — это capability: подписанный, короткоживущий на задачу, несёт маршрут, бюджет, модели и скоуп. Тогда даже утёкший ключ почти бесполезен — умирает с задачей, ограничен бюджетом одного workflow и ходит только в прокси. Плюс egress-allowlist: наружу только на прокси и реестры пакетов.

Брошенные контейнеры и реконсиляция при рестарте

высокий

Оркестратор упал после спавна — контейнер живёт, жжёт деньги, держит worktree. После рестарта оркестратор не знает, что бежит.

Лечение: TTL/таймаут внутри самого контейнера (а не только в оркестраторе), reaper, который сверяет живые контейнеры с известными задачами, и процедура реконсиляции состояния на старте.

Мозг в критическом пути и недетерминирован

высокий

Малформный ответ, галлюцинированный план, недоступность или лимиты API Anthropic — и петля встаёт. Мозг может и зациклиться на перепланировании.

Лечение: валидация структурированного ответа мозга по схеме, ретраи, бюджет на число задач/глубину плана, и явный путь эскалации на человека, когда мозг не может выдать валидное решение.

Верификация — несущая стена

Агент «обыгрывает» тесты

критично

Гейт «тесты зелёные → правильно» хорош ровно настолько, насколько хороши тесты. Агент может удалить падающий тест, захардкодить ожидаемое значение или ослабить ассерты — и гейт станет зелёным на сломанной фиче. Это типовой режим отказа агентов.

Лечение: хук, запрещающий агенту править тест-файлы (если задача — не «написать тесты»); приёмочные тесты, написанные человеком, для критичных путей; гейты на покрытие и мутационное тестирование; ревью диффа на предмет «решил или обыграл». Тесты, сгенерированные дешёвой моделью, считай слабыми по умолчанию.

Экономика дешёвых ретраев может перевернуться

высокий

Если воркер фейлит 30–40% задач, а ты ретраишь 3× и потом эскалируешь на ведущую модель, фактическая стоимость успешной задачи может приблизиться к «просто взять модель получше». Дешёвая модель не равно дешёвая система.

Лечение: меряй стоимость на успешную задачу, а не на вызов. Бюджет-кэп на задачу. Маршрутизируй по типу задачи: тривиальное — дешёвым, склонное к фейлам — сразу мозгу.

Знания и авто-доки

База знаний как эхо-камера

высокий

Фича уехала с тонким недопониманием → doc-агент задокументировал неверное поведение как истину → этот документ извлекается для следующей задачи → ошибка размножается. База уверенно повторяет собственные заблуждения.

Лечение: доки заземляй на фактический дифф и тесты, а не на интерпретацию агента. Ревью доков человеком на критичных областях. Метаданные происхождения на каждом куске (из какой задачи/коммита).

Устаревание и противоречия в вектор-базе

высокий

Фичи меняются и удаляются. Если doc-агент только дописывает, база накопит куски про старое и новое поведение одной фичи, и retrieval будет отдавать оба.

Лечение: upsert по ключу фичи (старое → superseded, не удалять); retrieval по умолчанию только current; doc-задача на ретайр при удалении фичи; учёт отката деплоя (фича откатилась — доку отозвать).

Правила

Конфликты и приоритет правил

высокий

Много правил, добавляемых на лету, в трёх скоупах → конфликты неизбежны (глобальное говорит X, продуктовое — не-X). Мозг получает противоречивые инструкции.

Лечение: детерминированная модель приоритета (например, продукт перебивает глобальное), детект конфликтов в момент записи правила, и фиксация версии правил на задачу при дисптаче (для аудита и реплея).

Мягкие правила не обязывают

средний

Инъекция правила в бриф ≠ его соблюдение, особенно дешёвой моделью. Чем больше правил инъектишь, тем сильнее они размывают внимание и жгут контекст. У числа реально работающих мягких правил есть потолок.

Лечение: триаж — что обязано быть хуком/гейтом, а что остаётся советом. Не пытайся словами заменить принуждение для критичных запретов.

Разрастание правил без жизненного цикла

средний

«Добавлять на лету» без ретайра → сотни правил, многие устаревшие или противоречивые, никто не знает, какие применяются.

Лечение: владелец у каждого правила, срок пересмотра, и наблюдаемость — какие правила сработали, какие нарушались.

Исполнение и безопасность

Промпт-инъекция и песочница воркера

высокий

Воркер исполняет сгенерированный LLM код с доступом к Bash. Вредоносная инструкция может прийти из содержимого репозитория или из извлечённых доков и увести агента в деструктивные команды или эксфильтрацию.

Лечение: жёсткая песочница — без доступа к Docker-сокету, read-only монтирования где можно, лимиты ресурсов, egress-политика, и принцип «контейнер не хранит ничего ценного». Считай весь внешний текст недоверенным.

Автономный выкат в прод = радиус поражения

высокий

Самое страшное место — давать дешёвому агенту катить в прод без человека.

Лечение: прогрессивная доставка (canary), автооткат по метрикам, и обязательный человеческий аппрув на рискованных изменениях. Полностью без рук — только для заведомо безопасных классов задач.

Неконтролируемая стоимость

высокий

Автономные агенты + ретраи + эскалация на ведущую модель = неограниченные траты, если задача залипла в цикле.

Лечение: жёсткие бюджет-кэпы на задачу / продукт / глобально, kill-switch, и атрибуция стоимости (она же нужна для circuit breaker, а не только для биллинга). Конкретно: модельный прокси выдаёт виртуальный токен на workflow с бюджетом и набором моделей — отсюда точное «сколько и когда» и автоматический обрыв по достижении кэпа. Учёт денег требует прайс-таблицы по физической модели — токен ведущей и токен рабочей модели стоят по-разному, поэтому метр умножает usage на цену конкретного провайдера.

Прокси — единая точка отказа и поражения

критично

Через прокси идёт каждый модельный вызов — и людей, и роя, — а в нём же сходятся реальные ключи. Упал прокси — встало всё; скомпрометировали — утекли все ключи разом.

Лечение: держать его тонким (умный форвардер с учётом, не место для бизнес-логики), закладывать доступность раньше остальных сервисов, реальные ключи — в секрет-менеджере, а не в БД прокси открытым текстом. Харденинг прокси важнее, чем у прочих сервисов.

Дрейф совместимости провайдеров

высокий

«Anthropic-совместимый» совпадает на ~95%, но края разные: стриминг (SSE), tool-use блоки, prompt caching, count_tokens, формы ошибок и коды статусов — а на коды завязана retry-логика Claude Code. Незаметное расхождение тихо ломает воркеров.

Лечение: начать с тонкого прозрачного форвардера и добавлять нормализацию точечно, где конкретный провайдер реально укусил, — иначе горячий путь распухнет. Различия отслеживать в журнале.

Миграции: снапшот скрывает масштаб

критично

Подготовленный срез прода покрывает сценарии, но не объём. Запрос без индекса летает на 10к строк и ложит прод на 10М; ALTER мгновенный на маленькой таблице держит её минутами на большой. Снапшот это не ловит by design, смоук-тесты — тоже; видно только под объёмом. Цена ошибки — не красный тест, а прод-данные.

Лечение: статический линтер миграций (ловит небезопасные паттерны без данных), правило expand-contract (схему меняем обратносовместимо, в два релиза, отдельно от кода), деструктивные и блокирующие миграции — всегда через человеческий гейт.

Цепочка зависимостей

высокий

Агент свободно ставит пакеты, а модели галлюцинируют имена; атакующие эти имена заранее регистрируют (slopsquatting) — автономный агент сам притащит малварь. Плюс уязвимые версии и несовместимые лицензии.

Лечение: новые пакеты — только через человека, принуждено хуком (блок npm/pip install неизвестного) как один из гейтов автономии. Проекты приходят уже настроенными под быстрые фичи, так что новый пакет — редкое событие. SCA-скан в верификации, дисциплина lock-файла.

Дрейф моков от реальных сервисов

низкий

Тесты гоняются против мока соседнего сервиса; если реальный сервис уехал — всё зелёное, а на проде падает интеграция. Для CRM с кучей внутренних связей это была бы зона риска, но сервисы вы делаете сами и знаете, так что ситуация редкая.

Лечение: регенерить мок из контракта сервиса в CI, чтобы он не мог тихо разойтись с реальностью.

Мультипродукт, люди и наблюдаемость

Оркестратор на незрелом продукте

высокий

Сила Comuki — езда по рельсам (готовая архитектура, проверенные скиллы, жёсткие правила). Новый продукт рельсов ещё не имеет — он сам ищет форму. Натравить оркестратор на чистый лист = он генерит слоп быстрее, чем вы кладёте рельсы, и чистки больше, чем экономии.

Лечение — последовательность: рельсы кладутся до оркестратора, но «рельсы» это не «дописанный продукт», а свод правил (у вас уже есть md-конвенции C#) + драконовские анализаторы с первого дня. Comuki приходит на готовые правила, а скиллы вырастают из сделанного: удачная фича → скилл «как делать похожее» → следующая задача класса едет по нему. Тяжёлое — в оркестратор, мелочь (кнопку) — локально руками; решает человек.

Изоляция между продуктами

высокий

Продукты делят платформу, но их код, секреты, правила, знания и стоимость должны быть изолированы. Баг или атака в агенте одного продукта не должны доставать другой.

Лечение: модель арендности с первого дня — даже внутри монолита из 2–3 сервисов гоняй скоуп продукта через всю модель данных.

Сосуществование людей и агентов в одном коде

средний

Локальный Claude Code разработчика и автономный агент правят один репозиторий. Чей коммит победит, как разруливать конфликт автономного PR и человеческого.

Лечение: автономная система работает через PR, которые ревьюит человек, а не пушит в main напрямую. Понятное владение веткой/задачей.

Штамповка при сплошном ревью

высокий

Если человек обязан аппрувить всё, наступает усталость от аппрувов — он перестаёт реально смотреть, и гейт превращается в театр, дающий ложную уверенность. Это хуже, чем отсутствие гейта. Та же болезнь — у визуальных baseline (Q7).

Лечение: концентрировать ревью на немногих высокорисковых изменениях (по классу), делать его асинхронным и дешёвым (summary + дифф по требованию), снижать частоту по мере доверия (выборка вместо сплошного). Внимание человека — дефицитный ресурс.

Эвал-харнес — система оценки самой оркестрации

желательно

Правка правила/скилла/промпта или апгрейд модели влияет на все задачи сразу — как узнать, что починив одно, не сломал три других? Это регрессионные тесты не для кода продукта, а для самой Comuki: набор эталонных задач с известным правильным результатом, прогон после каждой правки управляющей плоскости — «было 19/20, стало 16/20 → откатить».

Желательный функционал, не обязательный для MVP. На старте свод правил мал и правки видны глазами, а грубую регрессию ловят те же анализаторы (сломал правило → проект не собрался). Ценность растёт вместе с размером свода — нужен, когда правил сотни и в голове уже не удержать. Бесплатное условие сейчас: каждый скилл, формируемый из удачной фичи, помечать как кандидат в эталонную задачу — тогда набор соберётся сам собой. Один артефакт, два применения: рельса и экзаменационный билет.

Артефакт прогона как единая запись

высокий

Контейнер сносится — и работа умрёт с ним, если её не вынуть. Нужна не только потоковая запись в журнал, но и рабочая папка прогона: что просили, план мозга, summary воркеров, дифы, скриншоты, результаты тестов, пины версий.

Лечение: на прогон — уникальный run-id (= trace-id журнала, не плодить второй) и артефакт в объектном хранилище (S3): тяжёлое и immutable там, метаданные и журнал в БД с указателем. Это разом аудит решений, сырьё для doc-агента и материал для debug-агента. Заложить retention (тысячи прогонов × тяжёлые дифы) и скоуп по продукту в ключе (артефакт Магазина не достаётся из-под Админки).

Смешанная ревизия правил в одном прогоне

высокий

Контейнеры тянут правила/скиллы свежими. Если поправить их посреди летящего пайплайна, ранние стадии сделаны по старому своду, поздние — по новому. Прогон собран из двух разных сводов, отладка врёт.

Лечение: пин ревизии управляющей плоскости на старте прогона (рефер в артефакте), все контейнеры берут именно его; правка действует со следующих запусков. Git управляющей плоскости становится зависимостью горячего пути запуска — держать живым/зеркалить, как прокси.

Наблюдаемость нодетерминированной распределённой системы

высокий

Когда фича уехала сломанной, проследить причину через решения мозга + прогоны воркеров + правила + извлечённый контекст — тяжело. Без этого ты слеп.

Лечение: trace-id на каждую задачу; журнал фиксирует бриф, версии правил, модель, токены, стоимость, результаты верификации и дифф. Это «бортовой самописец» — без него отладка автономного роя невозможна.

Дыры на стыках компонентов

Отдельный класс: не внутри компонентов, а на швах. Закономерность — «описано действие, не назначен актёр / назван поток без контракта». Решения одного рода: назначить актёра и привязать к существующему состоянию (lease, git-коммит, строка в Postgres), а не плодить сущности.

Где бежит верификация

высокий

Воркер не судит себя сам, но и оркестратору не нужен харнес у себя.

Решение по природе: воркер запускает проверки и репортит сырьё (exit code, вывод линтера, passed/failed, JSON Playwright) — факты, не самооценка. Оркестратор детерминированно выносит green/red над сырьём, без модели. Достаточность тестов — внешний слой (хук на тест-файлы + человеческая приёмка). Окружения/фреймворки/линтеры — вход от разрабов; оркестратор их запускает. StageReport несёт сырьё, не status:green.

Вердикт по фиче

высокий

Объективное судит оркестратор. «Сделано ли то, что просили» в MVP — человек: выкатка в тестовый контур → смотрит → да/нет → оркестратор исполняет вердикт (двигает/останавливает DAG). Автономного «модель сама решила» в MVP нет — согласовано с ручным выкатом в прод.

Heartbeat доказывает жизнь, не прогресс

высокий

pi завис на медленном провайдере → контейнер жив, heartbeat идёт, работа стоит — зомби с lease.

Решение: два таймера. Liveness (контейнер/Translator жив) ловит краш/OOM. Progress (когда было последнее событие от pi) — Translator привязывает к потоку stdout; тишина дольше порога → stall. Прогресс меряется потоком событий, не таймером.

Гонка знаний при параллельных фичах

высокий

doc-агент пишет после прода → окно, где фича выкачена, но не задокументирована → пересекающиеся фичи не видят друг друга → дубль.

Решение: изучатель смотрит две вещи — базу знаний (задокументировано) И состояние активных прогонов у оркестратора (что в работе, какие области трогает). Это знание о текущих работах, живёт в состоянии оркестратора (Postgres), не в Knowledge. Окно схлопывается с часов до секунд; мердж/человек — backstop.

Приоритет правил, два источника

средний

Проектные (репо) и воркер-правила (dashboard) — про разные плоскости (стиль кода vs разрешения), конфликта почти нет.

Решение: на замках воркер-правила — потолок, проектные под ним (проектное не ослабляет safety-рейл). В «как делать» специфичное (проектное) бьёт общее. Сливает comuki-agent-core.

Общий контракт между параллельными контейнерами

средний

Бек и фронт в разных worktree читают один OpenAPI — где он, чтобы видели одну версию?

Решение: контракт — код; стадия «контракт» коммитит OpenAPI в ветку фичи, worktree бека/фронта ответвляются от этого коммита → идентичный контракт у обоих. «Одна версия» = один коммит. Тайминг — зависимостью в DAG.

TTL ключа против длительности стадии

средний

Ключ с настенным TTL протухает под долгой стадией.

Решение: прокси тупой и независимый (проверяет ключ локально, без БД на горячем пути), оркестратор отзывает ключ событийно по факту смерти воркера/lease. Жизнь ключа = жизнь работы; мёртвый воркер теряет ключ сразу. TTL — грубый backstop.

Схема событий C# ↔ TS

высокий

Бриф (оркестратор → агент) и payload отчёта (агент → Translator) пересекают C#↔TS и текут постоянно — рассогласование молча ломает всё. Comuki-события Translator↔оркестратор — C#↔C# (компилятор ловит); формат pi — не наш.

Решение: C# первичен, TS-типы генерятся из C# (C#→TS эмиттер), не нейтральная схема. Кодоген — после стабилизации; в Slice 0 руками. Узкий шов: только бриф + payload отчёта.

Гонка стоп против завершения

средний

Человек жмёт стоп (4 хопа), а воркер тем временем закончил.

Решение: арбитр — машина состояний в Postgres; стоп и завершение — переходы одной строки, БД сериализует, первый коммит выигрывает. Стоп после завершения не выбрасывает артефакт (стопит продвижение по DAG); завершение после стопа архивируется, не мёржится. Одна строка, атомарный переход.

Контракт ведущая ↔ оркестратор (Q1)

высокий

Главный шов, первый код. Модель stateless — оркестратор передаёт срез состояния под каждый вызов.

Форма: четыре типизированных решения, каждое со своим срезом — план (факты изучателя + каталог стадий + summary правил → DAG); бриф (спека + отобранный контекст + стадия); вердикт (сырьё + критерии → green/red, в автономии); ремонт (артефакт провала + история → стратегия фикса). Каждый вызов schema-валидируется; вывод модели не идёт в действие без валидации. Конкретные схемы — первый код.

09Технологический стек

Имя платформы — Comuki. Слои связаны не общим языком, а протоколами (MCP, HTTP, контейнеры, structured JSON), поэтому полиглот здесь by design, а не запах: каждый слой на своём языке, разговаривают по контракту.

  • comuki-orchestrator — C#. Control plane: durable-workflow (Temporal / Dapr), состояние, диспетчинг контейнеров, вызовы ведущей модели.
  • comuki-proxy — C#. Модельный прокси на YARP: виртуальные ключи, маршрутизация роль → физическая модель, метринг и бюджеты.
  • comuki-mcp — C#. MCP-сервер знаний и правил (официальный C# SDK для MCP). Единый платформенный рантайм с оркестратором.
  • agents (3 пакета) — TypeScript. comuki-agent-core (общее: типы событий, MCP, декларативные правила, формат брифа/отчёта) + comuki-worker-sdk (pi, воркеры) + comuki-dev-sdk (Claude Code, разрабы; форк GSD по происхождению). Принуждение — механикой каждого sdk; остальное — в ядре.
  • comuki-dashboard — React + shadcn/ui. Наблюдение и настройка; та же дизайн-система, что принуждает воркеров (§06).

Платформа целиком на C# по трём причинам, и все три бьют в дизайн. Перформанс и ресурсы — .NET кратно экономичнее на горячих путях (стриминг в проксе, сотни одновременных workflow в оркестраторе), это прямая экономия на железе. Durable-workflow, YARP и async-стек закрывают тяжёлые места из §08 (надёжность оркестратора, hot-path прокси) выбором движка, а не кодом. И команда — C#-разработчики: на родном стеке человеческий гейт из MVP острее, тонкий баг ловится в ревью, который на чужом языке проскочил бы. Плагин остаётся на TS — это домашний язык экосистемы Claude Code, и шов «платформа ↔ плагин» проходит ровно по MCP.

Агентов два под две ситуации. Воркеры → pi (pi-coding-agent): контроль процесса, дерево сессий, малый контекст, наблюдаемость — чего не хватало в Claude Code. Разрабы → форк GSD под Claude Code: зрелый интерактивный UX. Comuki держит внешний цикл (оркестрация, расписание, гейты, durable), агент — внутренний цикл задачи. Оба правил не хранят: проектные из репо, воркер-правила от оркестратора. Дыра «разные правила у воркеров и людей» закрыта природой (декларативное — единый текст; принуждающее — маленький набор замков механикой каждого агента). GSD форкаем без upstream (был rug-pull); research-фазу — на comuki-mcp.

Довод «модель плохо знает свежую библиотеку» снимается не языком, а подготовкой: агент пишет не под капризный API по памяти, а по вашему обкатанному скиллу. Подготовленная экосистема превращает незнакомую модели либу в знакомый агенту паттерн — поэтому агенту «проще на всём», если архитектура и обёртки готовы заранее.

Условие, на котором держится выбор

следить

Подготовленная экосистема скиллов — это обязательство, а не данность: скилл на каждый типовой кусок платформенной работы, обёртки над движущимися либами (MCP SDK, durable-движок), обкатанные локально до того, как их увидит рой.

Иначе: если экосистема отстанет от того, что агенты пытаются делать, вернётся галлюцинация по сырым API. Риск новизны либ не исчезает — он переносится в дисциплину поддержки скиллов. Версии движущихся библиотек пиновать жёстко (тот же дрейф версий, что у моделей, только в зависимостях).

И граница, которую стек не размывает: Comuki дирижирует, агенты — это Claude Code в контейнерах. Платформа их не реализует, а запускает, передаёт бриф и читает структурированный результат. Поэтому язык платформы и язык агентов независимы — видят друг друга только через MCP, HTTP и процессы.

10Принятые решения

По ходу проработки все архитектурные развилки дозрели до решения. Сначала — что входит в MVP, а что отложено (MVP — ассистируемый пайплайн, а не автономный рой), затем зафиксированные решения и то, что остаётся выбором реализации.

Объём MVP
В MVP

Задачи ставите вы руками — продуктовое решение «то ли это» живёт в самой постановке, отдельного гейта не нужно. Техническую сторону ведёт ведущая модель по готовым правилам проекта (архитектура и структура уже есть, изобретать почти нечего). Человек видит мысли агента, план, дифф и действия и может вмешаться, но не обязан судить каждый план. Система применяет проверенные скиллы-рецепты, обкатанные локально. Окружения — готовые шаблоны от девопсов, агент трогает только свою базу. Эвал-харнес — желательный, не обязательный (на старте прикрыт анализаторами). Новые пакеты и деструктивные миграции — только через человека.

Отложено

Полная автономия с классами изменений и храповиком доверия; merge-queue для многих фич сразу; большие фичи (их пока делаем руками). Доменный пользователь (знает предметную область, не код) — отдельная фаза со своим слоем intake и приёмки, включается после MVP продукта и покрытия ~80% правилами и скиллами. Это фаза «потом», а не выпавшие из дизайна куски.

Решено
Q1

Контракт «оркестратор ↔ мозг». Четыре типа решений, каждый — строгая валидируемая схема: синтез изучателя, план (DAG + контракт OpenAPI + брифы), вердикт, эскалация/ремонт. Вход — срез состояния с запиненными правилами; между вызовами мозг stateless, loop держит не он.

Q2

Гранулярность. Единица = стадия = контейнер = один проверяемый артефакт. Параллелизм — фронт/бек split на контракте. Стабильный фейл стадии → планировщик режет бриф мельче (адаптивно).

Q3

Граница автономии. Матрица по классам изменений плюс два гейта: аппрув плана (после изучателя) и аппрув деплоя. Старт консервативный, расширение авто-классов по аналитике фейлов.

Q4

Ключи. Свой модельный прокси: контейнеру дают виртуальный URL и виртуальный ключ (capability — маршрут, бюджет, модели, скоуп, TTL), реальные ключи живут в прокси, маршрутизация моделей — серверная. Закрывает утечку, egress-контроль и атрибуцию стоимости в одной точке.

Q5

Ветвление. Фича = базовая ветка от main; лейны (бек+миграция, фронт) — worktree от базы фичи; синхронизация мерджит лейны в ветку фичи → PR в main. Лейны ребейзятся на базу фичи, не на main.

Q8

Потолок стоимости на фичу. Виртуальный токен на workflow несёт бюджет и circuit-breaker; кэп считается на всю фичу, а не только на стадию.

Надзор

Человек — обработчик исключений, не вахтёр. Надзор концентрированный (по классу риска), асинхронный (ревью staged-результата, не блок пайплайна), дешёвый (summary + дифф по требованию) и убывающий (храповик доверия → выборка).

Q6

Соответствие контракту. Структурно — кодоген из OpenAPI (типизированные стабы для бека, клиент + mock для фронта): дрейф формы становится ошибкой компиляции. Поведенчески сверху — schema-валидация в preview. Спека версионируется и входит в план-аппрув, ведь её пишет агент.

Q7

Жизненный цикл визуальных baseline. Агент предлагает обновление, апрувит человек (асинхронно, before/after в той же поверхности ревью). Диф на нетронутом компоненте — жёсткая регрессия; на тронутом — предложение обновить baseline; новый компонент — эталон после vision-проверки на дизайн-систему. Baseline в репозитории, апдейт через тот же PR.

Q9

Бюджеты прокси. Гибрид: гарантированная партиция ёмкости для людей и критичных workflow, овербукнутый общий пул для терпеливого роя с бэкпрешером. Развести две кнопки — бюджет-кэп (деньги, circuit-breaker) и политику ёмкости (throughput). Scheduling — единственное место, где прокси легитимно умнеет.

Уровень реализации

Архитектурных развилок не осталось — дальше это выборы реализации, а не структуры: какой именно кодоген из OpenAPI, strict-priority против weighted-fair-queue в планировщике прокси, конкретные версии библиотек. Они решаются при написании и не меняют форму системы. Эволюция управляющей плоскости (дебаг → PR → эвал-харнес → новый рефер) — это пост-MVP dev-loop поверх той же модели; где физически живёт git правил и SDK — тоже выбор реализации.

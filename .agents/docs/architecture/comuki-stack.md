# Comuki — технический стек

> Из чего собрана платформа: языки, сервисы, хранилища, наблюдаемость. Дополняет архитектурный документ — там «что система делает», здесь «из чего сделана».

**Платформа: C# / .NET · Плагин: TypeScript · Дашборд: React + shadcn · Развёртывание: self-hosted**

Технический стек · черновик для обсуждения

## 01. Принципы выбора

Стек выбран под три ограничения из архитектуры: платформа целиком self-hosted (своё облако, ничего не уходит наружу), команда — C#-разработчики, а воркеры провайдер-агностичны и тупы. Из этого следуют два правила, по которым отбирались инструменты.

**Минимум движущихся частей, но не в ущерб гарантиям.** Не разводим по разным системам то, что должно меняться согласованно (состояние и очередь — одна транзакционная граница), но и не пихаем в одно вещи с разным профилем нагрузки (метрики и логи — не в транзакционную БД). Граница проходит по природе данных, а не по удобству.

**Тупой одинаковый воркер, вся специфика по API.** Контейнер-воркер один и тот же для любой стадии, продукта и модели — он стартует пустым и сам идёт за работой (pull-модель). Это развязывает платформу от механизма запуска: один `Dockerfile`, неважно Docker или k8s.

## 02. Компоненты репозитория

Платформа целиком на C#, агенты (pi + GSD) на TS, дашборд на React. Слои связаны протоколами (gRPC, MCP, HTTP), а не общим языком.

- **comuki-orchestrator** — C# / ASP.NET Core. Control plane: машина состояний DAG, pull-очередь задач, расписание, ретраи, диспетчинг воркеров, вызовы ведущей модели. Владеет источником правды и журналом.
- **comuki-proxy** — C# / YARP. Модельный прокси: виртуальные URL+ключи, маршрутизация роль → физическая модель, метринг, бюджеты, приоритет «люди > рой».
- **comuki-mcp** — C# (официальный MCP C# SDK). Сервер знаний и правил: retrieval, движок правил. Единый рантайм с оркестратором.
- **comuki-agent-core** — TypeScript. Общее ядро обоих sdk: типы событий, MCP-доступ к знаниям, чтение декларативных правил, формат брифа/отчёта. Единый код — дрейфу негде взяться.
- **comuki-worker-sdk** — TypeScript. Воркеры: pi-coding-agent (контроль, наблюдаемость, малый контекст) + pi-расширения с адаптерами принуждения.
- **comuki-dev-sdk** — TypeScript. Разрабы: Claude Code (интерактивный UX) + наши хуки. Форк GSD по происхождению, имя по роли.
- **comuki-dashboard** — React + shadcn/ui. Наблюдение и настройка; та же дизайн-система, что принуждает воркеров.

 03Запуск воркеров: pull-модель
 Воркер стартует «пустым» — в образе нет ничего про конкретную задачу. Он сам стучит в оркестратор за работой. Это делает контейнер тупым и одинаковым, а платформу — независимой от механизма запуска.

## 03. Запуск воркеров: pull-модель

Полный цикл — не просто «спросил и ушёл», а **claim → lease → heartbeat**: воркер клеймит задачу, получает бриф, роль модели, виртуальный ключ и git-ref правил, затем периодически шлёт heartbeat «я жив». Перестал стучать (упал, завис, OOM) — аренда истекает, оркестратор переназначает задачу. Без heartbeat pull-модель не отличит «думает» от «сдох»; с ним — это самовосстанавливающаяся очередь.

Внутри контейнера эту связь держит **Translator** (`Comuki.Platform.Worker.Translator`, AOT-бинарь) — двунаправленный мост между агентом (pi) и оркестратором. Он запускает pi как дочерний процесс, держит его stdout напрямую, переводит сырой stream-json в типизированные события и шлёт оркестратору; обратно принимает команды (`Stop`, `InjectContext`). Translator переводит и исполняет, но не решает — ретрай/эскалация/мердж/стоп-по-бюджету у оркестратора (у него состояние задачи, бюджет, DAG; у Translator'а нет). Канал Translator ↔ оркестратор — **gRPC** (сервис-сервис, двунаправленный типизированный стрим; общие proto → рассогласование ловит компилятор). Дашборд ↔ оркестратор — **SignalR** (браузеры). Разные швы — разный транспорт.

> **Почему не привязываемся к k8s/Docker напрямую** — Абстракция запуска — тонкий интерфейс «дай ещё воркер», за которым может быть `docker run`, k8s Job или под из пула. Оркестратор не настраивает контейнер под задачу — он ждёт, когда тот сам придёт за работой. Можно начать на голом Docker API и переехать в k8s, не трогая логику оркестрации.

## 04. Хранилища

Граница проходит по природе данных. То, что должно быть транзакционно согласовано, живёт вместе; то, что отличается профилем нагрузки, разводится.

| Что | Чем | Почему |
|---|---|---|
| **Состояние + очередь**DAG, статусы, pull-очередь | PostgreSQL`FOR UPDATE SKIP LOCKED` | Одна транзакционная граница: «задача взята» и «состояние обновилось» — в одной транзакции. Разнести = распределённая транзакция на ровном месте. |
| **Журнал событий**append-only, реал-тайм | PostgreSQL`LISTEN/NOTIFY` | Источник правды и пуш в дашборд из той же БД. |
| **Знания (вектора)**доки, рецепты, правила | pgvector(или Qdrant) | Справочные, не обязаны быть согласованы с прогоном в одной транзакции — единственное место, где вынос в отдельный движок оправдан по вкусу. |
| **Артефакты прогонов**дифы, скриншоты, summary, логи | MinIO (S3) | Тяжёлые immutable-блобы под `run-id/`. Метаданные в Postgres с указателем на объект. |
| **Пакеты и образы**NuGet, npm, базовый образ | Nexus | Приватный реестр + supply-chain-щит: воркер тянет зависимости только отсюда. |

> **MinIO и Nexus — разные звери, оба нужны** — **MinIO** — объектное хранилище под артефакты *выполнения* (что рождается в прогоне). **Nexus** — репозиторий *зависимостей* (откуда тянутся библиотеки и образы при сборке). Не альтернатива друг другу. Nexus заодно закрывает supply-chain двойной защитой: хук не даёт *попросить* новый пакет, а Nexus не даёт его *достать* из публичного реестра, даже если попросили. Slopsquatting перекрыт на уровне инфраструктуры, а не только правилом.

## 05. Durable-выполнение: развилка

Workflow фичи живёт долго (часы) и должен переживать падения оркестратора — это требование из рисков (at-least-once, идемпотентность). Два пути, и выбор зависит от того, сколько механики надёжности писать самим против администрировать.

| Путь | Плюс | Минус |
|---|---|---|
| **Postgres-only**claim/lease/heartbeat руками | Минимум инфраструктуры, всё в одной БД, полный контроль | Ретраи, таймауты, переживание падений пишете и отвечаете сами |
| **+ Temporal**durable-движок | Надёжность, версионирование и наблюдаемость из коробки; заточен под agentic-нагрузки | +1 серьёзный сервис в своём облаке; self-hosted Temporal надо администрировать |

**Рекомендация для MVP: Postgres-only.** claim/lease/heartbeat — это немного кода, а инфраструктуры на порядок меньше; для self-hosted старта это меньше операционной боли. Temporal — как «потом», если durable-логика разрастётся (сложное версионирование workflow, высокая пропускная способность). Версионирование управляющей плоскости (P7) при этом всё равно держится на git-ref, а не на движке.

## 06. Наблюдаемость: три слоя

У нодетерминированного роя наблюдаемость — несущая, а не приятная. Три слоя отвечают на три разных вопроса, поэтому это три инструмента, а не один раздутый.

| Вопрос | Слой | Чем |
|---|---|---|
| **Сколько / как часто**стоимость, токены, фейлы, латентность | Метрики | OpenTelemetry → VictoriaMetrics |
| **Что писали сервисы**логи прогонов и платформы | Логи | VictoriaLogs |
| **Где застряло**трасса прогона по стадиям | Трейсы | OpenTelemetry (trace-id = run-id) |
| **Что именно сделал агент**дифы, скриншоты, summary | Артефакты | MinIO (см. §04) |

Связка: метрики говорят «прогон дорогой и фейлит», трейс — «завис на шаге X», артефакт — «вот что агент там написал». сколько · где · что

OpenTelemetry-инструментирование закладывается с первого дня — .NET поддерживает его нативно, на старте дёшево, а когда надо понять «почему фича уехала сломанной» — бесценно. Бизнес-метрики (стоимость на успешную фичу, доля задач с первого прохода) идут туда же, что и технические — это один time-series с разными лейблами, разводить их незачем.

## 07. API и контракты

Три разных стиля общения по трём разным границам — каждый под свою задачу.

| Граница | Стиль | Зачем |
|---|---|---|
| Воркер ↔ оркестратор | HTTP/REST (claim, heartbeat, отчёт) | Простой pull-контракт; воркер тупой, ему нужен минимум |
| Дашборд ↔ оркестратор | REST + поток (SignalR/SSE) | Запросы + живые обновления прогонов в реал-тайме |
| Агент ↔ comuki-mcp | MCP | Знания и правила; единый протокол для воркеров (pi) и разрабов (GSD) |
| Сервисы → модели | через comuki-proxy (Anthropic Messages) | Виртуальные ключи, метринг, маршрутизация роли |

> **Один источник правды для контрактов** — формат брифа/отчёта между Translator и оркестратором — это C#↔C# (один язык, компилятор ловит рассогласование). Стык с TS-агентом (pi) уже: бриф/отчёт как JSON. На старте описываем в `Api.Contracts`; если стык разрастётся — единый JSON Schema, из которого генерятся обе стороны.

# Дизайн: ротация ключей Z.AI в модельном прокси

> Дата: 2026-06-23 · Статус: утверждён дизайн, ожидает написания плана
> Фаза: Phase 5 (Slice 1 — Proxy & Virtual Keys), первый вертикальный срез

## Проблема

Воркер-агент (`pi`) ходит к модели Z.AI (роль «рабочая модель», GLM)
через `ANTHROPIC_BASE_URL`. Когда у физического ключа Z.AI исчерпывается
дневная квота/баланс, апстрим начинает отвечать ошибкой, и агент встаёт.
Нужно, чтобы прокси **прозрачно** подменял исчерпанный ключ на следующий
живой из пула и повторял запрос — агент продолжает работать, не видя сбоя.

## Решение (кратко)

Реализуем ротацию ключей как **первый вертикальный срез** модельного
прокси Phase 5. Поднимаем тонкий YARP-хост `Comuki.Platform.Proxy` и
кладём логику ротации в `Comuki.Platform.Routing`. Прокси форвардит запрос
агента на Z.AI через YARP `IHttpForwarder`; при сигнале исчерпания квоты
(до старта стрима клиенту) помечает ключ в cooldown, берёт следующий и
повторяет. Виртуальные ключи с подписью, роутинг роль→модель, метеринг,
бюджеты и egress-allowlist — **следующие срезы Phase 5**, вне этой спеки.

### Объём (scope)

В объёме:
- Тонкий YARP-хост `Comuki.Platform.Proxy` (`application/internal/`).
- Логика ротации в `Comuki.Platform.Routing` (`feature/`): пул ключей,
  детектор исчерпания, retry-оркестрация, конфиг.
- Структурный лог события ротации.
- Юнит- и интеграционные тесты.

Вне объёма (следующие срезы Phase 5 / позже):
- Виртуальные ключи (подпись, TTL, capability/скоуп).
- Роутинг роль→физическая модель как таблица.
- Метеринг, бюджеты, kill-switch, атрибуция стоимости.
- Egress-allowlist, секрет-менеджер (здесь ключи берутся из
  конфига/env; интеграция с Vault — позже).
- Fallback на другого провайдера (напр. MiniMax) при исчерпании всего
  пула Z.AI — отдельный срез, требует роутинга по провайдерам.
- Полная OTel-инструментация (Phase 9) — здесь только структурный лог.

## Архитектура и размещение

Два новых проекта (правило «application тонкий», project-structure §«Где
логика, где хост»):

```
platform/src/
├── application/internal/
│   └── Comuki.Platform.Proxy/          # тонкий YARP-хост: Program.cs, эндпоинт, DI
└── feature/
    └── Comuki.Platform.Routing/        # логика: пул ключей, детектор, retry-оркестрация
```

`Proxy` не содержит бизнес-логики — поднимает Kestrel, маппит catch-all
эндпоинт на Anthropic-пути (`/v1/messages` и пр.) и делегирует в `Routing`.
`pi` знает только `ANTHROPIC_BASE_URL` = адрес прокси. Протокол на обоих
концах один (Anthropic-совместимый), поэтому прокси **пробрасывает** поток,
а не транслирует.

## Компоненты (в `Comuki.Platform.Routing`)

Четыре самостоятельных юнита, каждый с одной ответственностью.

### 1. `IKeyPool` / `KeyPool`
Владеет ключами Z.AI и их состоянием.
- `TryAcquire()` → «живой» ключ (не в cooldown) либо `null`, если все в
  cooldown.
- `MarkExhausted(key, retryAfter?)` → cooldown до времени из `Retry-After`,
  иначе на `DefaultCooldown` из конфига.
- Состояние потокобезопасное, **в памяти** одного инстанса прокси
  (несколько воркеров бьют параллельно → общий пул). При рестарте прокси
  пул перечитывается из конфига, cooldown сбрасывается — это безопасно
  (в худшем случае один лишний пробный запрос на исчерпанный ключ).
- Не знает про HTTP.

### 2. `IQuotaExhaustionDetector` / `QuotaExhaustionDetector`
Чистая функция `(статус, заголовки, начало тела) → bool`.
- Применяет **настраиваемый список правил** (коды + паттерны тела):
  `429`, «insufficient balance», «quota exceeded», `401` на мёртвом ключе.
- Без состояния; легко расширять и тестировать на фикстурах.
- Не знает про пул.

### 3. `KeyRotatingForwarder`
Оркестратор retry-цикла — сердце фичи. Склеивает `KeyPool`, `Detector`
и YARP `IHttpForwarder`. См. «Поток запроса».

### 4. `RotationOptions`
Конфиг (`IOptions`): список ключей (из конфига/env), правила детекции,
`DefaultCooldown`, upstream-URL Z.AI.

## Поток запроса (с ротацией)

```
pi (воркер) ──POST /v1/messages──► Proxy (YARP host)
                                      │
                                      ▼
                            KeyRotatingForwarder.Forward()
   ┌──────────────────────────────────────────────────────────┐
   │ 1. buffer = прочитать тело запроса в память (для повтора)  │
   │ 2. loop (max попыток = размер живого пула):                │
   │      key = KeyPool.TryAcquire()                            │
   │      если null → выход из цикла (все в cooldown)           │
   │      ответ = IHttpForwarder.SendAsync(upstream, key,       │
   │                                        buffer)             │
   │      если Detector.IsExhausted(ответ):                     │
   │          KeyPool.MarkExhausted(key, ответ.Retry-After)     │
   │          лог-событие "key_rotated" → continue              │
   │      иначе:                                                │
   │          стримить ответ агенту как есть → ВЫХОД (успех)    │
   │ 3. цикл исчерпан → 503 + Anthropic-совместимое тело ошибки │
   └──────────────────────────────────────────────────────────┘
```

Что держит бесшовность:
- **Буферизация тела запроса.** Тело (Anthropic messages payload) читается
  в память один раз, чтобы повторить на новом ключе. Может быть большим
  (контекст) — допустимо; без буфера повтор невозможен.
- **Детект до стрима клиенту.** Решение «исчерпан/нет» принимается по
  статусу+заголовкам+началу тела апстрима **до того**, как первый байт ушёл
  агенту. Поэтому ретрай не «рвёт» поток. Z.AI/GLM отдаёт quota/balance-
  ошибки в начальном HTTP-ответе → попадаем в безопасный путь.
- **Подмена `Authorization`** на выбранный физический ключ — YARP request-
  transform; остальные заголовки и URL пробрасываются без трансляции.

## Обработка ошибок и крайние случаи

| Случай | Поведение |
|---|---|
| Все ключи в cooldown | `503 Service Unavailable` + Anthropic-совместимое тело (`{"type":"error","error":{"type":"overloaded_error",...}}`). Решение об эскалации — у **оркестратора**, не у прокси («прокси не решает»). |
| Не-quota ошибка апстрима (500, таймаут, сеть) | Детектор → `false` → проброс ошибки агенту как есть, ключ в cooldown **не** уходит. Ротация только по quota-сигналам. |
| Ошибка в середине стрима | Не ретраим (поток уже пошёл клиенту), пробрасываем как есть. Для quota практически не встречается. |
| `Retry-After` отсутствует | cooldown на `DefaultCooldown` из конфига. |
| Гонка: два воркера схватили один ключ до пометки | Оба ретраятся на следующих ключах; пул потокобезопасен, `MarkExhausted` идемпотентен. |
| Пустой пул на старте | Fail-fast: прокси падает на старте с понятной ошибкой, а не отдаёт 503 в рантайме. |

**Наблюдаемость:** каждая ротация — структурное событие в лог
(`key_rotated`: исчерпанный ключ, на какой переключились, сигнал-причина,
до какого времени cooldown). Соответствует принципу «всё — событие в
журнале». Полная OTel — Phase 9.

## Тестирование

Стек (Phase 3): xUnit v3 (MTP) + Shouldly + NSubstitute. Размещение —
`platform/tests/Comuki.Platform.Routing.Unit.KeyRotation/` (конвенция
`<SrcProject>.<Kind>.<Feature>`).

Юнит-тесты:
- `QuotaExhaustionDetector` — таблица фикстур из реальных ответов Z.AI
  (429 + «insufficient balance», 401, обычный 500, успех 200) → ожидаемый
  `bool`. Самый ценный набор: детекция должна быть точной.
- `KeyPool` — `TryAcquire` пропускает cooldown-ключи; `MarkExhausted` с
  `Retry-After` и без; все в cooldown → `null`; потокобезопасность.
- `KeyRotatingForwarder` (NSubstitute-моки `IHttpForwarder`, `IKeyPool`) —
  первый ключ исчерпан → второй → успех; все исчерпаны → 503; не-quota
  ошибка → проброс без ротации; число попыток ограничено размером пула.

Интеграционный тест `Comuki.Platform.Proxy.Integration.Rotation`:
- `WebApplicationFactory` + фейковый «Z.AI» апстрим (тестовый Kestrel-стаб):
  на первый ключ — 429-quota, на второй — успешный SSE. Проверяем: клиент
  получил успешный стрим + в логах есть `key_rotated`. End-to-end без
  реального Z.AI.

Покрытие — в пределах 70%-гейта проекта.

## Открытые вопросы / зависимости

- **Точный формат quota-ответа Z.AI/GLM** — правила детектора заданы
  настраиваемым списком; конкретные коды/паттерны уточнить по докам Z.AI на
  этапе плана (или итеративно дополнять при наблюдении реальных ответов).
- **Источник ключей** — здесь конфиг/env; миграция на секрет-менеджер
  (Vault) — отдельный срез Phase 5.

  в оркестраторе.

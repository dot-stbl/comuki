# AGENTS.md — правила фронтенда и визуального тестирования

> Стек: **React + Vite + shadcn/ui (Tailwind) + Storybook**.
> Цель: качественный структурный UI без «нейрослопа». Любой UI-компонент
> проходит три слоя: **(1) ограничения до генерации → (2) детерминированные
> тесты → (3) цикл визуальной критики со скриншотами.**
>
> Это не пожелания, а правила. Нарушение пунктов из раздела «Жёсткие
> ограничения» = ошибка, которую нужно исправить, а не обсуждать.

---

## 0. Главный принцип

Ты **не видишь верстку по коду**. «Кривой отступ», «поехавшая сетка»,
«элементы не выровнены» нельзя поймать чтением JSX/CSS — только глядя на
отрендеренный результат. Поэтому ни один UI-компонент не считается готовым,
пока ты не **снял его скриншот в Storybook и не прошёл по рубрике из раздела 4**.

«Выглядит хорошо» без скриншота и без прохода по чек-листу — запрещённый ответ.

## 1. Жёсткие ограничения (источник слопа — свобода, лишаем её)

### Spacing и сетка
- Базовая сетка — **4px** (шкала 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64).
  Все отступы кратны 4. Предпочитать кратность 8 для крупных блоков.
- Отступы — **только утилитами Tailwind** (`p-*`, `gap-*`, `space-*`).
- **ЗАПРЕЩЕНЫ arbitrary-значения**: никаких `p-[13px]`, `mt-[17px]`,
  `w-[437px]`, `gap-[10px]`. Если нужного значения нет в шкале — значит
  макет неверен или нужно добавить токен, а не хардкодить пиксель.
- Layout строится через `flex`/`grid` + `gap`. **Не** разносить отступы
  марджинами на дочерних элементах вразнобой.
- Не смешивать способы задания одного отступа (либо `gap` на контейнере,
  либо `space-y`, не оба).

### Токены и стили
- Цвета, радиусы, тени, типографика — **только из токенов shadcn**
  (CSS-переменные / темы). Никаких голых hex (`#3b82f6`) в компонентах.
- Радиусы — из шкалы темы (`rounded-sm/md/lg/xl`), один язык скруглений
  на весь компонент.
- Тени — из шкалы (`shadow-sm/md/lg`), не придумывать `shadow-[...]`.

### Компоненты
- Сначала **переиспользовать примитивы shadcn/ui** (Button, Card, Dialog,
  Input, …). Свой компонент — только если в shadcn нет аналога.
- Варианты (size/variant/state) — **только через `cva`** + `cn()`
  (`tailwind-merge`). Не плодить булевы пропсы под каждый стиль.
- Семантика: интерактив — это `<button>`/`<a>`, а не `<div onClick>`.
  Каждое поле формы имеет `<label>`. Изображения имеют `alt`.

### Типографика и иерархия
- Размеры шрифта — из шкалы темы (`text-sm/base/lg/...`), не произвольные.
- Видимая иерархия: заголовок / подзаголовок / тело различимы по размеру и
  весу. «Всё одного размера» — это слоп.
- Ширина текстовых колонок ограничена (`max-w-prose` / разумный `max-w-*`),
  длинные строки не растягиваются на весь экран.

## 2. Конвенции историй Storybook

Каждый компонент сопровождается историями — это и тестовая поверхность,
и то, что ты будешь скриншотить.

- Стори на **каждое значимое состояние**: `Default`, `Loading`, `Disabled`,
  `Error`, `Empty`, `WithLongText` (переполнение!), и крайние случаи.
- Использовать `args` + `argTypes`, включить `autodocs`.
- Состояния не «прятать» — каждое отдельной историей, чтобы каждое можно
  было снять и проверить.
- Поведение (клики, фокус, ввод) покрывать `play`-функциями.

Изолированный URL истории для скриншота (без чрома Storybook):

```
http://localhost:6006/iframe.html?id=<story-id>&viewMode=story
```

## 3. Детерминированные тесты (CI-гейт — ловят регрессии, не вкус)

Стек Storybook 9/10. Истории исполняются как component-тесты в реальном
браузере (Vitest browser mode на базе Playwright).

Установка (один раз):
```bash
npx storybook add @storybook/addon-vitest
npx storybook add @storybook/addon-a11y
npx storybook add @chromatic-com/storybook   # визуальная регрессия (облако)
# либо локальная альтернатива без облака:
# npm i -D storybook-addon-vis
```

Что гоняем на каждом PR:
1. **Component-тесты** — каждая история рендерится без ошибок в браузере.
2. **a11y (axe)** — контраст, label, семантика. Это объективная часть
   качества; нарушения axe = красный CI.
3. **Визуальная регрессия** — снапшоты против эталона (Chromatic или
   `storybook-addon-vis`). Ловит непреднамеренные визуальные изменения.
4. **Interaction-тесты** (`play`) — поведение.
5. **Lint** — `eslint-plugin-better-tailwindcss` (или `eslint-plugin-tailwindcss`)
   с запретом arbitrary-значений и enforce порядка классов. Любой `[Npx]` = красный.

> Этот слой ловит регрессии и объективные дефекты, но **не отвечает**, хорош ли
> сам дизайн. За это отвечает слой 4.

## 4. Цикл визуальной критики (обязателен перед «готово»)

Инструмент: **Playwright MCP** (`browser_navigate`, `browser_resize`,
`browser_take_screenshot`, чтение DOM/`getComputedStyle`).

### Процедура для каждого компонента
1. Запустить Storybook, открыть изолированный iframe истории.
2. Снять скриншот в **трёх вьюпортах**: `375` (mobile), `768` (tablet),
   `1440` (desktop). Сетка и layout ломаются именно на брейкпоинтах.
3. Пройти **полностью** по рубрике ниже, по каждому пункту.
4. Выписать **конкретные дефекты**: какой элемент, что не так, какое
   значение должно быть. Не «выглядит неаккуратно», а
   *«у `.card-header` `margin-left: 13px` — нет в шкале 4px, должно быть `ml-3` (12px)»*.
5. Исправить → переснять → повторять, пока рубрика не чистая.

### Рубрика (проходить по каждому пункту, не пропускать)
1. **Сетка**: все отступы кратны 4 (предпочтительно 8)? Нет «почти-значений»?
2. **Ритм отступов**: расстояния консистентны? Нет соседних `16px` и `20px`
   без причины?
3. **Выравнивание**: элементы выровнены по краям/осям? Оптическое
   выравнивание соблюдено (иконка+текст, числа в таблице)?
4. **Радиусы/тени/типографика**: один язык на весь компонент, всё из токенов?
5. **Переполнение**: длинный текст не ломает layout, нет обрезки, нет
   горизонтального скролла на 375px?
6. **Иерархия и плотность**: видна структура (заголовок/тело/действия)?
   Не «всё одинаковое»? Не слишком плотно/разреженно?
7. **Контраст**: текст читаем на фоне (сверить с результатом axe)?
8. **Состояния**: hover/focus/active/disabled/loading выглядят корректно и
   отличимы?
9. **Адаптив**: на 375 / 768 / 1440 ничего не сломано, контент перетекает
   логично?

### Подтверждать глазомер цифрами (ключевой приём)
Скриншот говорит «криво», но это субъективно. По подозрительным элементам
**читать `getComputedStyle` через Playwright** и сверять с разрешённой шкалой.
Тогда дефект становится объективным и сразу чинится:

> `getComputedStyle($0).marginLeft === "13px"` → не на шкале (4/8/12/16…)
> → исправить на `ml-3` (12px).

Эвристика по стоимости токенов: **структуру** (что во что вложено, какие
computed-стили) проверяй по DOM/accessibility-дереву — это дёшево и точно;
**скриншоты** делай для финального «гештальт-взгляда» и брейкпоинтов, не на
каждое мелкое изменение.

### Если есть макет (Figma и т.п.)
Экспортировать таргет-скриншот, считать pixel-diff (pixelmatch + pngjs)
между текущим состоянием и целью, править UI в сторону макета по diff-картинке.

## 5. Definition of Done для UI-компонента

Компонент готов, только когда:
- [ ] Использованы примитивы shadcn там, где возможно; варианты через `cva`.
- [ ] Ноль arbitrary-значений Tailwind; всё на шкале токенов (lint зелёный).
- [ ] Истории на все значимые состояния, включая `WithLongText`.
- [ ] Component-тесты и a11y (axe) зелёные.
- [ ] Визуальная регрессия зелёная (или baseline осознанно обновлён).
- [ ] Пройден цикл визуальной критики в 3 вьюпортах, рубрика чистая,
      подозрительные отступы подтверждены через `getComputedStyle`.

---

## 6. Анти-паттерны (это слоп — не делать)

- `p-[13px]`, `w-[437px]`, любые arbitrary-пиксели.
- Голые hex-цвета и `shadow-[...]` мимо токенов.
- `<div onClick>` вместо `<button>`; поля без `<label>`.
- Разнобой отступов марджинами вместо `gap`.
- «Всё одного размера», отсутствие иерархии.
- Свой компонент там, где есть shadcn-примитив.
- Ответ «выглядит хорошо» без скриншота и без прохода по рубрике.

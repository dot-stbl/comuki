# Comuki Dashboard — спецификация дизайн-системы

Вход для Claude Design. Это **наблюдательный (operational) интерфейс** под нодетерминированный рой агентов — ближе к Grafana / Linear / Temporal UI, чем к продуктовому CRM. Плотный, информационный, для кодеров. НЕ продуктовая дизайн-система CRM — та делается отдельно, вместе с продуктом.

Стек: React + shadcn/ui, реал-тайм через SignalR/SSE. Тёмная тема по умолчанию (operational-дашборды смотрят подолгу, тёмное меньше утомляет), со светлым вариантом.

---

## 1. Что этот UI должен делать

Дашборд отвечает на четыре вопроса о рое, и компоненты группируются под них:

1. **Что бежит прямо сейчас** — живые прогоны, на какой стадии, в каком окружении.
2. **Почему вот это повело себя так** — трейс прогона: бриф, версии правил, модель, токены, стоимость, результаты тестов, дифф.
3. **Что ждёт меня** — очередь аппрувов (план / деплой / обновление baseline).
4. **Сколько это стоит и где ломается** — стоимость по продукту/стадии, аналитика фейлов, стоимость на успешную задачу.

Плюс слой настройки (реестр приложений, правила, бюджеты, ключи, маршрутизация моделей) — формы и таблицы, менее визуально нагруженные.

---

## 2. Аesthetic direction

**Industrial / utilitarian, но не холодный.** Это приборная панель — приоритет плотности информации и читаемости статусов с одного взгляда, а не «красоты». Но с характером: тёплый нейтральный фон вместо мёртво-серого, один резкий акцент, моноширинный шрифт для всего машинного (id, токены, версии, время). Ощущение — «пульт управления, за которым проводят часы», а не «лендинг SaaS».

Дифференциатор, который должен запоминаться: **статус прогона читается мгновенно цветом и формой, без чтения текста** — состояние роя видно периферийным зрением.

---

## 3. Токены

### Цвет — тёмная тема (default)

| Роль | Значение | Применение |
|---|---|---|
| `bg` | `#1A1815` | фон приложения (тёплый чёрный, не #000) |
| `surface` | `#23201B` | карточки, панели |
| `surface-raised` | `#2B2722` | поднятые элементы, поповеры |
| `border` | `#3A352D` | разделители |
| `text` | `#EDE8DD` | основной текст |
| `text-muted` | `#9A9183` | вторичный |
| `accent` | `#C75D43` | терракота — главный акцент, действия |

### Семантика статусов (несущая — на ней держится «статус с одного взгляда»)

| Статус | Цвет | Где |
|---|---|---|
| `running` | `#4A90D9` (синий) | прогон/стадия в работе |
| `success` | `#3E9D74` (зелёный) | прошло, замержено, зелёный гейт |
| `failed` | `#C75D43` (терракота/красный) | красный гейт, краш |
| `waiting` | `#C99A3C` (янтарь) | ждёт человека / аппрува |
| `queued` | `#7A7468` (серый) | в очереди, не начато |
| `escalated` | `#9B6BC9` (фиолет) | ушло на ведущую модель / ремонт |

Острота риска (для раздела рисков/инцидентов): `critical` = красный, `high` = янтарь, `medium` = серый.

### Светлая тема

Тот же бумажный язык, что в документах Comuki: `bg #FAF7F0`, `surface #fff`, `text #26241E`, `accent #B0472F`. Статусы те же, чуть темнее для контраста на светлом.

### Типографика

- **Display / заголовки**: характерный засечный или гротеск с характером — НЕ Inter/Roboto. (В документах Comuki использован Fraunces — можно взять его для единства бренда.)
- **Body**: чистый читаемый — Spectral или аналог.
- **Mono**: IBM Plex Mono — ОБЯЗАТЕЛЬНО для всего машинного: run-id, trace-id, токены, стоимость, версии правил, git-ref, таймстампы, длительности. Это половина текста на дашборде.

### Метрики формы

- Радиус: `6px` карточки, `4px` мелкие элементы (бейджи, кнопки). Сдержанно, не «пухло».
- Отступы: плотная сетка `4px`-база. Operational UI = высокая плотность, но с дыханием между блоками.
- Тени: минимум; глубина через `surface-raised` и border, не через дроп-шэдоу.
- Моушн: сдержанный. Пульсация на `running`-статусе (мягкий «дышащий» индикатор), плавное появление новых событий в ленте. Никаких декоративных анимаций — это пульт.

## 4. Компоненты — общие (атомы)

- **StatusBadge** — пилюля со статусом из семантики выше. Цвет + точка-индикатор; `running` пульсирует. Должен читаться без текста.
- **RunIdChip** — моноширинный чип с id прогона, кликабельный, с copy-to-clipboard.
- **CostTag** — стоимость (`$0.42`) и/или токены, моно, с маленьким значком модели.
- **ModelBadge** — какая роль/модель (ведущая/рабочая), нейтральный бейдж; физическую модель показываем тонко (tooltip), т.к. архитектурно мы говорим ролями.
- **DurationLabel** — длительность стадии/прогона, моно, живая (тикает для running).
- **RiskTag** — острота (critical/high/medium) для инцидентов и рисков.
- **VersionRef** — git-ref управляющей плоскости (свод правил + версия SDK), моно, кликабельно к деталям ревизии.

---

## 5. Компоненты — по разделам

### 5.1 Живые прогоны («что бежит сейчас»)

- **RunCard** — карточка прогона: run-id, приложение, заголовок задачи, общий статус, текущая стадия, прошедшее время, накопленная стоимость. Лейбл приложения цветом/меткой (мультиарендность видна).
- **StagePipeline** — горизонтальная/вертикальная цепочка стадий с DAG-ветвлением (изучатор → план → контракт → [бек ∥ фронт] → синхронизация → тесты → деплой → doc). Каждая стадия — узел со статусом; параллельные лейны (бек/фронт) показаны рядом. Это центральный, фирменный компонент — на него смотрят чаще всего.
- **LiveRunsBoard** — сетка/лента RunCard с фильтром по приложению и статусу, обновление в реал-тайме.
- **WorkerIndicator** — занятость пула воркеров, heartbeat-здоровье (живой/завис/переназначен).

### 5.2 Трейс прогона («почему так»)

- **RunTimeline** — вертикальная лента событий прогона (append-only журнал): что просили, план мозга, старт/финиш каждой стадии, retry, эскалация, гейты. С таймстампами (моно).
- **BriefViewer** — бриф, который получил воркер на стадию (читаемый, с подсветкой применённых правил).
- **DiffViewer** — дифф изменений (код), syntax-highlight, сворачиваемый по файлам.
- **TestResultPanel** — результаты гейта по слоям: типы/линт/юнит (зелёное/красное), Playwright E2E, визуальный слой.
- **VisualReviewCard** — before/after скриншоты компонента (Storybook baseline vs новый), для аппрува обновления baseline.
- **ArtifactLink** — ссылка на артефакт прогона в MinIO (summary, логи, скриншоты) — «открыть полную запись».
- **RevisionPanel** — какой свод правил/версия SDK были запинены на этот прогон (для воспроизводимости и debug-агента).

### 5.3 Очередь аппрувов («что ждёт меня»)

- **ApprovalQueue** — список того, что ждёт человека: тип (план / деплой / baseline), приложение, давность, краткое summary.
- **ApprovalCard** — карточка одного аппрува с summary сверху и диффом/деталями по требованию (раскрывается). Кнопки: одобрить / отклонить / выдернуть на ревью. Дизайн под «аппрув за 30 секунд» — summary решает, детали по клику.
- **PlanReviewView** — план задачи (DAG стадий + контракт) для план-аппрува, с допущениями планировщика, вынесенными наружу.

### 5.4 Стоимость и фейлы («сколько и где ломается»)

- **CostBreakdown** — таблица/график стоимости по приложению / стадии / модели, тренды во времени.
- **CostPerSuccess** — ключевая бизнес-метрика: стоимость на *успешную* задачу (не на вызов), с разбивкой.
- **FailureAnalytics** — где падают стадии, частота ретраев, на чём чаще эскалация на ведущую.
- **BudgetMeter** — занятость бюджета прокси / пула ключей, индикатор приближения к кэпу, kill-switch.

### 5.5 Настройка (формы, менее визуально нагружены)

- **AppsRegistry** — реестр приложений: репо, стек, окружения, цели деплоя.
- **RulesEditor** — правила: добавление, скоуп (глобально/приложение/стадия/тип), мягкие vs жёсткие, версии, детект конфликтов.
- **AutonomyMatrix** — границы автономии по классам изменений (что авто, что через человека).
- **ModelRouting** — маппинг роль → физическая модель, политика эскалации.
- **KeysPanel** — провайдеры, скоупы, ротация, конфиг прокси.
- **EvalHarnessView** (желательный, не MVP) — прогон golden-задач, сравнение «было/стало» при правке правил.

## 6. Layout

- **Шелл**: левый узкий навигейт (иконки разделов: прогоны / аппрувы / стоимость / знания / настройки), верхняя строка с глобальным статусом роя (сколько бежит / ждёт / упало) и kill-switch.
- **Глобальный статус-бар** — всегда виден: сводка состояния роя цветными счётчиками (по семантике статусов). Это «приборная панель» в буквальном смысле — состояние системы периферийным зрением.
- **Плотность**: таблицы и ленты — основной носитель. Карточки для прогонов и аппрувов. Не лендинг — экраны рассчитаны на долгий просмотр и быстрый скан.

---

## 7. Что НЕ делать

- Не делать это похожим на маркетинговый SaaS-лендинг — это пульт, не витрина.
- Не использовать Inter/Roboto/system-шрифты и фиолетовые градиенты на белом (generic AI-эстетика).
- Не прятать статусы за текстом — цвет и форма первичны.
- Не смешивать с продуктовой дизайн-системой CRM — это разные системы, общий только бренд-токен (акцент, шрифт).

---

## 8. Подсказка для Claude Design

Начать стоит с трёх фирменных экранов, которые задают язык всей системы:
1. **LiveRunsBoard** со StagePipeline — центральный экран, самый показательный.
2. **RunTimeline + DiffViewer** — экран трейса одного прогона.
3. **ApprovalQueue + ApprovalCard** — экран «что ждёт меня».

Если эти три согласованы и читаемы — остальное достраивается по их образцу. Токены и StatusBadge зафиксировать первыми, они пронизывают всё.

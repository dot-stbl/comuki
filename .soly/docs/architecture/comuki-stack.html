Comuki — стек репозитория

Из чего собрана платформа: языки, сервисы, хранилища, наблюдаемость. Дополняет архитектурный документ — там «что система делает», здесь «из чего сделана».

Платформа: C# / .NET Агенты: pi + GSD (TS) Дашборд: React + shadcn Развёртывание: self-hosted

01Принципы выбора

Стек выбран под три ограничения из архитектуры: платформа целиком self-hosted (своё облако, ничего не уходит наружу), команда — C#-разработчики, а воркеры провайдер-агностичны и тупы. Из этого следуют два правила, по которым отбирались инструменты.

Минимум движущихся частей, но не в ущерб гарантиям. Не разводим по разным системам то, что должно меняться согласованно (состояние и очередь — одна транзакционная граница), но и не пихаем в одно вещи с разным профилем нагрузки (метрики и логи — не в транзакционную БД). Граница проходит по природе данных, а не по удобству.

Тупой одинаковый воркер, вся специфика по API. Контейнер-воркер один и тот же для любой стадии, продукта и модели — он стартует пустым и сам идёт за работой (pull-модель). Это развязывает платформу от механизма запуска: один Dockerfile, неважно Docker или k8s.

02Компоненты репозитория

Платформа целиком на C#, плагин на TS, дашборд на React. Слои связаны протоколами (MCP, HTTP), а не общим языком.

  • comuki-orchestrator — C# / ASP.NET Core. Control plane: машина состояний DAG, pull-очередь задач, расписание, ретраи, диспетчинг воркеров, вызовы ведущей модели. Владеет источником правды и журналом.
  • comuki-proxy — C# / YARP. Модельный прокси: виртуальные URL+ключи, маршрутизация роль → физическая модель, метринг, бюджеты, приоритет «люди > рой».
  • comuki-mcp — C# (официальный MCP C# SDK). Сервер знаний и правил: retrieval, движок правил. Единый рантайм с оркестратором.
  • comuki-agent-core — TS. Общее ядро обоих sdk: типы событий, MCP-доступ, чтение декларативных правил, формат брифа/отчёта. Единый код — дрейфу негде взяться.
  • comuki-worker-sdk — TS. Воркеры: pi (контроль, наблюдаемость) + pi-расширения принуждения.
  • comuki-dev-sdk — TS. Разрабы: Claude Code (UX) + наши хуки. Форк GSD по происхождению, имя по роли.
  • comuki-dashboard — React + shadcn/ui. Наблюдение и настройка; та же дизайн-система, что принуждает воркеров.

03Запуск воркеров: pull-модель

Воркер стартует «пустым» — в образе нет ничего про конкретную задачу. Он сам стучит в оркестратор за работой. Это делает контейнер тупым и одинаковым, а платформу — независимой от механизма запуска.

Полный цикл — не просто «спросил и ушёл», а claim → lease → heartbeat: воркер клеймит задачу, получает бриф, роль модели, виртуальный ключ и git-ref правил, затем периодически шлёт heartbeat «я жив». Перестал стучать (упал, завис, OOM) — аренда истекает, оркестратор переназначает задачу. Без heartbeat pull-модель не отличит «думает» от «сдох»; с ним — это самовосстанавливающаяся очередь.

Внутри контейнера связь держит Translator (Comuki.Platform.Worker.Translator, AOT) — двунаправленный мост Claude Code ↔ оркестратор. Запускает claude -p дочерним процессом, держит его stdout, переводит stream-json в типизированные события и шлёт оркестратору; обратно принимает команды (Stop, InjectContext). Переводит и исполняет, не решает — ретрай/эскалация/стоп у оркестратора (у него состояние задачи и бюджет; у Translator'а нет). Канал — gRPC (сервис-сервис, двунаправленный типизированный стрим, общие proto). Дашборд ↔ оркестратор — SignalR (браузеры). Разные швы — разный транспорт.

Почему не привязываемся к k8s/Docker напрямую

Абстракция запуска — тонкий интерфейс «дай ещё воркер», за которым может быть docker run, k8s Job или под из пула. Оркестратор не настраивает контейнер под задачу — он ждёт, когда тот сам придёт за работой. Можно начать на голом Docker API и переехать в k8s, не трогая логику оркестрации.

04Хранилища

Граница проходит по природе данных. То, что должно быть транзакционно согласовано, живёт вместе; то, что отличается профилем нагрузки, разводится.

MinIO и Nexus — разные звери, оба нужны

MinIO — объектное хранилище под артефакты выполнения (что рождается в прогоне). Nexus — репозиторий зависимостей (откуда тянутся библиотеки и образы при сборке). Не альтернатива друг другу.

Nexus заодно закрывает supply-chain двойной защитой: хук не даёт попросить новый пакет, а Nexus не даёт его достать из публичного реестра, даже если попросили. Slopsquatting перекрыт на уровне инфраструктуры, а не только правилом.

05Durable-выполнение: развилка

Workflow фичи живёт долго (часы) и должен переживать падения оркестратора — это требование из рисков (at-least-once, идемпотентность). Два пути, и выбор зависит от того, сколько механики надёжности писать самим против администрировать.

ПутьПлюсМинус
Postgres-only
claim/lease/heartbeat руками		Минимум инфраструктуры, всё в одной БД, полный контрольРетраи, таймауты, переживание падений пишете и отвечаете сами
+ Temporal
durable-движок		Надёжность, версионирование и наблюдаемость из коробки; заточен под agentic-нагрузки+1 серьёзный сервис в своём облаке; self-hosted Temporal надо администрировать

Рекомендация для MVP: Postgres-only. claim/lease/heartbeat — это немного кода, а инфраструктуры на порядок меньше; для self-hosted старта это меньше операционной боли. Temporal — как «потом», если durable-логика разрастётся (сложное версионирование workflow, высокая пропускная способность). Версионирование управляющей плоскости (P7) при этом всё равно держится на git-ref, а не на движке.

06Наблюдаемость: три слоя

У нодетерминированного роя наблюдаемость — несущая, а не приятная. Три слоя отвечают на три разных вопроса, поэтому это три инструмента, а не один раздутый.

Связка: метрики говорят «прогон дорогой и фейлит», трейс — «завис на шаге X», артефакт — «вот что агент там написал». сколько · где · что

OpenTelemetry-инструментирование закладывается с первого дня — .NET поддерживает его нативно, на старте дёшево, а когда надо понять «почему фича уехала сломанной» — бесценно. Бизнес-метрики (стоимость на успешную фичу, доля задач с первого прохода) идут туда же, что и технические — это один time-series с разными лейблами, разводить их незачем.

07API и контракты

Три разных стиля общения по трём разным границам — каждый под свою задачу.

ГраницаСтильЗачем

Дашборд ↔ оркестраторREST + поток (SignalR/SSE)Запросы + живые обновления прогонов в реал-тайме

Один источник правды для контрактов

Формат брифа/отчёта между Translator и оркестратором — C#↔C# (один язык, компилятор ловит рассогласование). Стык с TS-агентом (pi) уже: бриф/отчёт как JSON. На старте описываем в Api.Contracts; разрастётся — единый JSON Schema на обе стороны.

08Семейство .NET AI: что берём

«.NET AI» от Microsoft — это не один пакет, а семейство (Microsoft.Extensions.AI, VectorData, Agent Framework, MCP SDK, Evaluation). Берём из него выборочно — лакмус один: библиотека решает проблему, которую мы ещё не решили, или ту, что уже закрыта дизайном? Прокси и GSD закрыли два больших куска, поэтому дублирующие их библиотеки избыточны.

ПакетРешениеПочему
MCP C# SDKБерёмОснова comuki-mcp. Уже в стеке.
Extensions.AI.EvaluationБерём (потом)Готовый каркас под эвал-харнес: прогон golden-задач, кеш ответов, хранение результатов, отчёты. Не писать с нуля. Пост-MVP.
Extensions.VectorDataОпциональноАбстракция над вектор-стором — только если хочешь оставить дверь под смену pgvector → Qdrant. Иначе прямой клиент проще.
Extensions.AI (IChatClient)Не берёмАбстракция над провайдерами — но это уже делает прокси (развязка на уровне сети). Второй слой абстракции поверх того же.
Agent FrameworkНе берёмМногошаговые agentic workflow — дублирует оркестратор + GSD. Третий дирижёр в системе, где уже два. Категорически мимо.

Принцип на будущее

Каждый раз, глядя на готовую библиотеку (особенно «от Microsoft, вроде в тему»): закрывает ли она незакрытое (оценка, вектор-абстракция) или дублирует уже решённое дизайном (провайдеры → прокси, оркестрация → GSD)? Берём только первое.

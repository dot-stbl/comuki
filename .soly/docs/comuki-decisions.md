# Comuki — журнал решений

Слепок обсуждения: что решили и **почему именно так**, с альтернативами. Документы (`architecture`, `stack`, `designspec`) описывают итог; этот журнал — логику, чтобы будущий чат в проекте понимал основания, не перечитывая всё.

---

## Базовая форма системы

**Мозг думает, но не является позвоночником.** Один Claude Code агент не может быть оркестратором: его контекст копит всё (context-rot), падение убивает состояние, dashboard нельзя строить поверх «головы» LLM. Решение: детерминированный control plane + LLM только в планировании, контексте и ревью. «LLM предлагает — система распоряжается».

**Агенты stateless, эфемерные.** Контейнер = функция `(бриф + код) → (дифф + отчёт)`. Снос по дизайну, не баг. Единственное условие — извлечь результат до сноса (в git-ветку + структурированный отчёт).

**Внешний цикл (Comuki) vs внутренний (GSD).** Comuki дирижирует роем сессий; GSD дирижирует одной сессией. Берём у GSD внутренний цикл задачи, не его верхнюю оркестрацию — иначе два дирижёра конфликтуют.

## Модели

**Роли вместо вендоров.** Говорим «ведущая модель» (план/контракт/ревью/ремонт) и «рабочая модель» (стадийные воркеры). Физическая модель за ролью — маппинг в проксе, не часть архитектуры. Сейчас: ведущая = Opus, рабочая = GLM (z.ai) / MiniMax. Почему: развязка от вендора + смена модели = одна строка маппинга, не трогая структуру.

**Качество держится не на воркере, а на брифе + гейте верификации.** Раз рабочая модель слабая: жёсткий `allowedTools`, ригидный контракт вывода, мелкая нарезка. Ведущая — ещё и ремонтная бригада (эскалация после N провалов).

## Прокси (ключевое решение)

**Свой модельный прокси, а не managed-vault.** Закрывает разом: утечку ключей, egress-контроль, атрибуцию стоимости. Контейнер знает только `ANTHROPIC_BASE_URL` + токен → подсовываем виртуальный URL и виртуальный ключ, который понимает только прокси.

**Виртуальный ключ = capability**, не просто токен: несёт маршрут, бюджет, модели, скоуп, TTL; подписанный, короткоживущий. Утёкший ключ почти бесполезен. Реальные ключи провайдеров — в секрет-менеджере, который прокси читает.

**Маршрутизация моделей — серверная.** Роль → физическая модель резолвится в проксе (одна таблица), а не в env контейнеров. На YARP, т.к. протокол на обоих концах один (Anthropic-совместимый) — прокси пробрасывает поток, не транслирует → тонкий.

**Прокси — single point of failure и поражения.** Держать тонким, доступность раньше остального, харденинг важнее прочих сервисов.

## База знаний и документация

**Код и доки разделены.** Код в RAG НЕ индексируем — агент грепает в worktree (нативная сила Claude Code; RAG по коду устаревает). Доки/спеки/правила — в retrieval-стор, отдаём по MCP.

**Самообновляющиеся доки.** Фича в прод → событие → doc-агент документирует (вход уже есть: дифф/бриф/тесты) → upsert в вектор-базу. MCP знает **задокументированные фичи**; сырой код — агентный grep. Изучатор смотрит обе линзы.

**Upsert по ключу фичи**, не дописыванием (иначе старое+новое поведение одновременно). Старое → superseded, retrieval по умолчанию current.

## Workflow и параллелизм

**Contract-first.** Первый артефакт после плана — не код, а OpenAPI-контракт = шов фронт↔бек. Дальше параллельно: бек по спеке, фронт на mock из спеки → синхронизация на реальный OpenAPI. Риск — дрейф контракта; лечится contract testing + кодоген (дрейф формы = ошибка компиляции).

**Изучатор первым.** Read-only: грепает код + спрашивает MCP «такое уже есть?». Бьёт по дублирующим реализациям — худшему виду слопа.

**Окружения по этапам.** Каждая стадия — одноразовое окружение из схемы+конфига прода (не данных, не секретов). Прод касается только последняя стадия за гейтом → «сломать прод» невозможно по конструкции.

**Тест-фреймворк = гейт по слоям.** Детерминированное (типы/линт/юнит) → Storybook + vision-модель (ловит кривую вёрстку) → Playwright E2E. Раз агенты сами пишут тесты — они слабые: визуал-ревью + человеческие приёмочные обязательны, хук запрещает править тест-файлы.

## Управляющая плоскость как код (P7)

**Правила, скиллы, агенты, брифы версионируются как код.** Правятся через дебаг → ревью → эвал-харнес → новая версия. Человек ВСЕГДА замыкает петлю — авто-самоизменения нет.

**Версия пинится на прогон.** Контейнеры тянут зафиксированную ревизию (git-ref), не «последнюю» — иначе прогон собран из двух сводов правил. Правка действует со следующих запусков; перезапуск = новый прогон на новой ревизии.

**Debug-агент.** Застрял пайплайн / проблема перед продом → человек запускает debug-агента, тот читает артефакты прогонов, предлагает правку. Менять и одобрять — человек.

**Принцип: к агентской работе подходим как к домену разработки.** Скилл правится как код, дебаг агентского поведения = дебаг.

## Артефакты и наблюдаемость

**Артефакт на прогон в S3 (MinIO).** Уникальный run-id (= trace-id, не плодить второй): summary, дифы, скриншоты, логи, пины версий. Разом: аудит решений + сырьё для doc-агента + материал для debug-агента.

**Три слоя наблюдаемости** (разные вопросы → разные инструменты): метрики+логи (OTel → Victoria, бизнес туда же), трейсы (OTel, trace-id=run-id), артефакты (MinIO). «Сколько / где / что».

## Стек

**Платформа целиком C#/.NET** (orchestrator, proxy на YARP, mcp на C# SDK, Translator на AOT). Причины: перформанс на hot-path (стриминг, много workflow); durable-движок/YARP закрывают риски выбором, не кодом; команда — C#-кодеры → острее человеческий гейт. Агенты воркеров и оболочка разрабов — не C# (pi и GSD на TS). Швы между языками — gRPC (Translator↔оркестратор) и MCP (агент↔знания).

**Подготовленная экосистема скиллов снимает «модель не знает свежую либу»** — агент пишет по обкатанному скиллу, не по памяти. Это обязательство, не данность.

**Два агента под две ситуации, три пакета.** Воркеры → **pi** (`comuki-worker-sdk`): контроль и наблюдаемость, которых не хватает в Claude Code. Разрабы → **Claude Code** (`comuki-dev-sdk`, форк GSD — имя по роли, не по происхождению; GSD остаётся как источник форка, без upstream, rug-pull-история, пин версий). Общее ядро **`comuki-agent-core`** шарят оба sdk: типы событий, MCP-доступ, чтение декларативных правил, формат брифа/отчёта — пишется один раз, разъехаться не может. Принуждение (замки) — НЕ в core, своя механика у каждого (pi-extensions vs Claude Code hooks). Рассматривали один агент на всё — контроль на воркерах перевесил. Рантаймы (pi, Claude Code) берутся готовыми, ваши — три TS-пакета поверх.

**Два свода правил по природе, а не по месту.** Это сняло мнимую проблему «один свод в два места → дрейф»: сводов два, и они про разное.
- *Проектные правила/скиллы* — лежат в репозитории проекта (нужны только этому проекту, едут одной ревизией с кодом). Берут оба: разраб (сидит в репе), воркер (выкачивает репо). Один источник — дрейфу негде взяться.
- *Воркер-правила* (поведение роя: меньше свободы, ограничения автономных) — задаются в **dashboard**, живут у оркестратора, едут только воркеру. Человека не касаются.
Воркер складывает оба свода; разраб берёт только проектные. Дрейфа нет, потому что общей копии, которая могла бы разъехаться, не существует — каждый свод в одном месте.

**Translator — мост воркер ↔ оркестратор.** AOT-бинарь в контейнере воркера (`Comuki.Platform.Worker.Translator`). Запускает агента (pi) дочерним процессом, держит его stdout, переводит поток в типизированные события, шлёт оркестратору; обратно принимает команды (Stop, InjectContext). **Переводит и исполняет, не решает** — у него нет состояния задачи/бюджета/DAG, поэтому ретрай/эскалация/стоп физически не могут жить в нём, только в оркестраторе. Отказались от «оркестратор читает stdout снаружи» (хрупко, особенно в k8s) и от entrypoint-дирижёра (второй мозг в контейнере). Translator — именно канал.

**Транспорты по природе шва.** Translator ↔ оркестратор — **gRPC** (сервис-сервис, двунаправленный типизированный стрим, общие proto → рассогласование ловит компилятор). Dashboard ↔ оркестратор — **SignalR** (браузеры, real-time UI). Не сводим в один ради «прикольнее»: SignalR слабо-типизирован, потерял бы компайл-тайм проверку воркерного шва.

**Подготовленная экосистема скиллов снимает «модель не знает свежую либу»** — агент пишет по обкатанному скиллу, не по памяти. Это обязательство, не данность.

**Pull-модель воркеров.** Контейнер стартует пустым, сам идёт в API за работой (claim → lease → heartbeat). Тупой одинаковый образ, развязка от k8s/Docker. Heartbeat обязателен — иначе не отличить «думает» от «сдох». «Тупость» — про отсутствие *решений*, не кода: Translator в контейнере есть, но он только мост.

**Хранилища по природе данных.** Postgres = состояние + очередь (`FOR UPDATE SKIP LOCKED`) + журнал + вектора (pgvector) — одна транзакционная граница. MinIO = артефакты (блобы выполнения). Nexus = пакеты/образы (supply-chain-щит, ≠ MinIO). Метрики НЕ в Postgres (разный профиль) → Victoria.

**Durable: Postgres-only на старте**, Temporal — потом (если durable-логика разрастётся). Версионирование управляющей плоскости держится на git-ref, не на движке.

## MVP против «потом»

**В MVP:** задачи ставим руками (продуктовое решение — в постановке); техническую сторону ведёт ведущая модель по готовым правилам; человек видит всё, может вмешаться, не обязан судить каждый план; проверенные скиллы; окружения от девопсов; новые пакеты и деструктивные миграции — через человека; выкат в прод вручную; **драконовские анализаторы (Roslyn, warnings-as-errors) — несущая опора качества**.

**Отложено:** полная автономия с классами/храповиком доверия; merge-queue для многих фич; большие фичи (руками); эвал-харнес (желательный, на старте прикрыт анализаторами); доменный пользователь — после MVP продукта + ~80% покрытия правилами/скиллами.

## Узкие места (нетехнические — главные)

1. **Оркестратор на незрелом продукте.** Сила Comuki — езда по рельсам, а новый продукт рельсов не имеет. Лечение: рельсы (свод правил + анализаторы) до оркестратора; «рельсы» = существующие md-конвенции C# + жёсткий тулинг, не «дописанный продукт». Скиллы растут из сделанного.
2. **Холодный старт знаний/эвалов.** База пустая на старте — сеем существующими правилами; эвал-эталоны копятся из скиллов по ходу (помечать каждый скилл как кандидат).
3. **Два класса пользователей.** Кодеры (MVP) vs доменщики (потом, свой слой intake/приёмки). Не «появится само».
4. **Миграции под объёмом и перформанс под нагрузкой** — единственное, что человек-в-петле НЕ ловит глазами (видно только на проде). Линтер миграций + expand-contract.

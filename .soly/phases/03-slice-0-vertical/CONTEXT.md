# Phase 3 — Slice 0 Vertical Slice

## Цель

Один тривиальный тикет проходит через систему от начала до конца. Проверяем
три бумажных допущения на реальности: **pull-модель**, **Translator/gRPC**,
**пригодность pi**. После этой фазы фундамент Comuki — не бумажный.

Подробный план шагов и rationale — `.soly/docs/comuki-slice-0.md` (читать
целиком перед `soly plan 3`).

## Что входит

- **3.1 — Sanity-check pi headless.** Запустить `pi` вручную с тривиальным
  промптом, вывод в stream-json, проверить: запускается неинтерактивно,
  парсимый поток событий, ходит к модели. Если pi не подходит — здесь же
  проверить `claude -p`, развилка решается на живом.
- **3.2 — Postgres + claim.** Таблицы `runs` / `tasks` (или `runs` / `stages` /
  `tasks` по итогам 3.1). `FOR UPDATE SKIP LOCKED` + lease. Тест: два
  клеймера одновременно не берут одну задачу; протухший lease → возврат в
  пул. Reaper для протухших lease.
- **3.3 — Translator запускает pi и парсит вывод.** `Comuki.Platform.Worker.Translator`
  (C# AOT) делает `Process.Start(pi)`, читает stream-json, парсит в типизированные
  события (`StageReport`, `StageActivity`). Без gRPC — пока печатает в stdout.
- **3.4 — gRPC Translator ↔ Orchestrator.** Bi-di стрим. Orchestrator видит
  события в реал-тайме, может прислать `Stop`.
- **3.5 — Контейнер замыкает цикл.** `worker.Dockerfile` = pi + Translator.
  Orchestrator: insert task → spawn container → Translator клеймит, запускает
  pi на тривиальном брифе ("создай файл `hello.txt` с заданным содержимым") →
  стримит события назад → Orchestrator логирует финальный `StageReport` →
  контейнер умирает, lease освобождён.

## Что НЕ входит

- Прокси / виртуальные ключи — Phase 4.
- Knowledge / MCP — Phase 5.
- Реальная верификация (типы/линт/юнит) — Phase 6.
- DAG, многостадийность, contract-first, фронт/бек — Phase 7.
- Дашборд — Phase 7.
- Reaper протухших lease в `pi`-контейнере — базовый claim (3.2) сначала;
  reaper — поверх в этом же слайсе.

## Definition of Done

Из `comuki-slice-0.md` § Definition of Done:

> Запускаешь одну команду → задача попадает в Postgres → поднимается контейнер
> → pi делает тривиальное изменение кода → оркестратор видит структурное
> событие «готово» с результатом → контейнер умирает, lease освобождён → ты
> наблюдал весь путь в логах.

## Hard constraints

- **Translator — AOT-бинарь**, не managed. Тонкий, быстрый старт, едет
  в `CMD` контейнера.
- **События между Translator и Orchestrator — типизированные** (общий
  `.proto`, рассогласование ловит компилятор).
- **Контейнер = чистая функция** `(бриф + код) → (дифф + отчёт)`. Никакой
  памяти между запусками.
- **Атомарность "задача взята + lease поставлен"** — в одной транзакции.
- **Lease-TTL внутри контейнера**, не только в Orchestrator (риск
  "брошенных контейнеров" из architecture.md §08).

# Phase 4 — Slice 1: Proxy & Virtual Keys

## Цель

Убрать реальные API-ключи из контейнера-воркера. Всё общение с моделью идёт
через `Comuki.Platform.Proxy` на YARP; контейнер знает только виртуальный URL
и виртуальный capability-ключ.

Подробное обоснование — `.soly/docs/comuki-decisions.md` § "Прокси (ключевое
решение)" и `.soly/docs/comuki-architecture.md` § 04.

## Что входит

Заполняется в `soly plan 4`. Ожидаемый scope:

- `Comuki.Platform.Proxy` (ASP.NET Core + YARP) — тонкий entry, никакой
  бизнес-логики. Pass-through с подменой URL+ключа.
- `Comuki.Platform.Routing` — feature: роль→физическая-модель, capability
  виртуального ключа, метринг, бюджеты.
- Формат виртуального ключа: подписанный, короткоживущий (TTL на задачу),
  несёт route/budget/scope/TTL. Утёкший ключ почти бесполезен.
- Secret-manager integration — stub на этом этапе (реальный провайдер — Vault
  или managed, решим по deploy-окружению).
- Egress allowlist: наружу — прокси, Nexus, ничего больше.
- Приоритет "люди > рой" — принуждается на уровне прокси.
- Метрики: cost-per-app, cost-per-stage, cost-per-agent.
- Удалить временный "прямой ключ" из шага 0 Slice 0 — теперь воркер ходит
  только через прокси.

## Что НЕ входит

- Per-key policies UI — Phase 7 (дашборд).
- Qdrant vs pgvector — зафиксировано pgvector (можно пересмотреть в Phase 5,
  если нагрузка упрётся).
- Kill-switch по бюджету — Phase 6 (тут только метрика, не action).

## Зависит от

Phase 3 (нужен реальный трафик воркеров, чтобы маршрутизировать).

## Definition of Done

Заполняется в `soly plan 4`. Ожидаемые проверки:

- Воркер с подсунутым виртуальным ключом проходит Slice 0 DoD **без знания**
  реального ключа.
- Утёкший виртуальный ключ отвергается прокси через TTL.
- Метрики cost-per-stage появляются в VictoriaMetrics.
- Сценарий "рой под нагрузкой + локальный Claude Code разраба" — прокси
  отдаёт приоритет человеку (latency p99 человеческих запросов не растёт).

## Hard constraints

- **Прокси — single point of failure** (decisions.md). High availability важнее
  остальных сервисов; харденинг — здесь.
- **Протокол на обоих концах один** (Anthropic Messages) — прокси пробрасывает
  поток, не транслирует. Тонкий.
- **Реальные ключи — НИКОГДА в env контейнера**, только в secret-manager,
  который читает прокси.
- **Capability-ключ ≠ просто токен** — несёт маршрут, бюджет, модели, скоуп,
  TTL. Это и есть разница с "просто подписанным JWT".

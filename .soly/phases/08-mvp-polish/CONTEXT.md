# Phase 8 — MVP Polish

## Цель

Система переживает собственные ошибки. At-least-once durability, три слоя
наблюдаемости, эвал-харнес на golden-задачах. Платформу можно отдать в
production-like эксплуатацию.

Подробное обоснование — `.soly/docs/comuki-architecture.md` § 08 (риски) и
`.soly/docs/comuki-stack.md` § 06 (наблюдаемость).

## Что входит

Заполняется в `soly plan 8`. Ожидаемый scope:

- OTel инструментирование **везде** (Orchestration, Translator, Proxy, MCP,
  Dashboard backend). Business + tech метрики в одном time-series с разными
  лейблами — разводить незачем (stack.md §06).
- VictoriaMetrics + VictoriaLogs в `deploy/docker-compose.yml`. Метрики
  (сколько), логи (что писали), трейсы (где застряло), артефакты в MinIO
  (что именно сделал агент) — три разных вопроса, три разных инструмента.
- Append-only event log: `trace-id = run-id`. Журнал — debug-интерфейс.
- Идемпотентность на dispatch / merge / deploy. Каждый необратимый шаг
  спрашивает "я это уже делал?" (архитектура §08, [критично] #1).
- Reaper для осиротевших контейнеров + реконсиляция состояния на старте
  Orchestrator (архитектура §08, [высокий] #3).
- Эвал-харнес scaffolding: golden-задачи из обкатанных скиллов (per decisions.md:
  "новый тип работы сначала становится проверенным скиллом, потом — доступным
  оркестратору").
- Coverage target: 70% line (TESTING-RULES §10), исключая Migrations /
  Program.cs / Generated.
- Onboarding-документ: новый разраб запускает весь цикл на чистом чекауте за
  ≤30 минут.
- Финальная верификация Slice 0 DoD и Slice 4 DoD на свежем окружении.

## Что НЕ входит

- Temporal upgrade — Postgres-only был осознанным MVP-выбором (stack.md §05).
  Возвращаемся, только если durable-логика перерастёт одну БД-транзакцию.
- Доменный пользователь (vs кодер) — после MVP продукта + ~80% покрытия
  правилами/скиллами (decisions.md § "Узкие места").
- Auto-deploy / full autonomy — non-goal для v1.
- Полная мульти-tenant аналитика — закладывается в Phase 7, полируется здесь.

## Зависит от

Phase 7.

## Definition of Done

Заполняется в `soly plan 8`. Ожидаемые проверки:

- Orchestrator убит посреди прогона → после рестарта реконсилирует состояние,
  lease'ы протухли, контейнеры умерли по TTL внутри, прогон не дублируется.
- Два клеймера бьются за одну задачу → одна победила, вторая получила
  "already taken" и пошла за следующей.
- Дрейф часов на 5 минут вперёд → lease'ы не ломаются (используем UTC
  everywhere).
- Новый разраб поднимает всю систему по README за ≤30 минут, прогоняет
  Slice 0 DoD.
- Покрытие 70% line, 0 critical/high рисков из architecture.md §08 не
  разрешены.

## Hard constraints

- **trace-id = run-id** — единственный ID на прогон. Не плодим второй.
- **Каждый необратимый шаг — пара (intent, outcome) в журнале**, в одной
  транзакции где возможно.
- **Idempotency keys** на dispatch / merge / deploy — обязательны.
- **Все метрики бизнеса и техники — один time-series** (стек §06).
- **Coverage 70% — разумный минимум**, не максимум. 80%+ ведёт к
  бессмысленным тестам ради метрики (TESTING-RULES §10).

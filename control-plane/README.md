# Comuki — Control Plane (text content, not code)

Воркер-правила и обкатанные скиллы. **Отдельно от проектных** (которые лежат в репо
продукта). Версионируются под git-ref, который **пинится на прогон** (decisions.md:
"Версия пинится на прогон" — иначе прогон собран из двух сводов правил).

## Структура

```
control-plane/
├── rules/worker/    # поведение роя (НЕ проектные правила)
└── skills/          # обкатанные рецепты
```

## `rules/worker/` — поведение роя

Что **рой** может/не может делать. Задаются через **dashboard** (Phase 7) — не через
коммиты в это репо. Касаются **только воркеров**, человеку не нужны.

Формат: YAML или Markdown, парсится Orchestrator'ом **в момент сборки брифа**
(per architecture.md § 05: "правила пинятся на прогон, читаются в момент сборки брифа,
не на деплое").

### Примеры (будущее содержимое)

- `budget.md` — кэпы: per-task / per-app / global, kill-switch
- `autonomy.md` — классы изменений: copy-правки → авто в прод, миграции → аппрув
- `tools.md` — `allowedTools` per роль (working model vs leading model)
- `retry.md` — N failed retries → эскалация на ведущую модель
- `schedule.md` — working hours, приоритеты "люди > рой"

## `skills/` — обкатанные рецепты

Глобальные playbook'и, не привязаны к конкретному продукту. Оркестратор подсовывает
их воркеру как **инструкцию "как это делать"** (не "что делать" — это в брифе).

Растут **из сделанного**: новая фича уехала в прод → оформили в skill → теперь
оркестратор знает как её повторить. Тот же skill → кандидат в golden-задачу
эвал-харнеса (Phase 8).

### Примеры (будущее содержимое)

- `add-crud-endpoint-aspnet.md` — что открыть, какой контроллер, какой DTO, какой тест
- `add-page-vite-react-shadcn.md` — где создать файл, как зароутить, как проверить
- `write-postgres-migration.md` — какой CLI, как именовать, какие conventions
- `add-favorite-button.md` — конкретный рецепт (из `comuki-architecture.md` § 06)

## Контраст с проектными правилами

| Свод | Где | Кто берёт |
|---|---|---|
| Проектные правила | В **репо продукта** (CRM etc.) | Разраб (сидит) + воркер (выкачивает репо) |
| Воркер-правила | Здесь, `control-plane/rules/worker/` | Только воркер (через Orchestrator) |
| Скиллы | Здесь, `control-plane/skills/` | Воркер (через Orchestrator при сборке брифа) |

**Воркер складывает оба свода правил.** Разраб берёт только проектные. Дрейфа нет,
потому что общей копии, которая могла бы разъехаться, **не существует** — каждый свод
в одном месте.

Это снимает мнимую проблему "один свод в два места → дрейф": сводов **два**, и они
про разное (decisions.md).

## Контент и оболочки — разный ритм

- `control-plane/` (rules, skills) — контент. Меняется часто, по мере роста скиллов
  и обнаружения новых ограничений.
- `agents/` (comuki-agent-core, worker-sdk, dev-sdk) — оболочки. Меняется реже,
  привязан к релизам SDK.

**Версионируются раздельно** (project-structure.md § 5: "Контент и оболочки агентов
версионируются раздельно — разный ритм изменений").

## Когда наполнять

| Папка | Phase | Что |
|---|---|---|
| `rules/worker/` | 7 (DAG + Dashboard) | Dashboard-формы для добавления/редактирования; v1-контент |
| `skills/` | 6+ (Verification) | По мере накопления рецептов из сделанного |

Phase 1–2: папки пустые, только `.gitkeep`. Не заполняем "на будущее" — каждый skill
должен быть **проверен на реальной фиче**, не выдуман.

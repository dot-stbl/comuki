# Proposal: Domain-user intake (slice 1 — Custom domain types)

## Why

The Comuki orchestrator already classifies incoming work by ticket kind and
admission source (chat, tracker webhook, native ticket). What it does **not**
classify yet is the **user-facing domain type** of the work — the question
"what kind of work is this, from the user's point of view?" (`code`, `data`,
`infra`, `research`, …). The post-1.0 backlog (`#11`) calls this slice
"Domain-user intake (без кода)" — without code means: classify from the
intake side, do not change the worker runtime yet.

Today every project runs every work item through a single default profile
(`implement`). A project that legitimately wants to route `code` work to
`implement` but `data` work to a different profile has no way to declare that
on the project. We add the smallest seam that lets a project make that
declaration, without reaching into the engine or the run launcher.

## What Changes

- `ProjectSettings` gains two fields: `domain_type` (enum
  `Standard | Custom | Hybrid`, default `Standard`) and
  `custom_domain_types_json` (`text`, nullable, a JSON object of
  `domain-type → profile-key`).
- A new `ProjectDomainTypeResolver` in the Projects application layer maps a
  domain-type string to a profile key, honouring the project's declared mode:
  - **Standard** projects use a single fixed profile key (`implement`) for
    every domain type — the existing default behaviour.
  - **Custom** projects ignore the default and resolve only against the JSON
    map; an unknown domain type is a typed error.
  - **Hybrid** projects try the standard default first, fall back to the JSON
    map; an unknown domain type is still a typed error.
- `ProjectSettingsView` and `ProjectMapper` expose the two new fields.
- `UpdateSettingsCommand` and `ProjectSettings.Apply` accept the new fields
  (optimistic concurrency is unchanged — same `version` column).
- The `projects.project_settings` table gains the two columns via an EF Core
  migration generated by `dotnet ef migrations add`.

## Capabilities

### New Capabilities

(none — this slice is purely additive inside the existing `projects`
capability)

### Modified Capabilities

- `projects`: `ProjectSettings` shape and a new application-layer resolver

## Impact

- `platform/src/modules/Projects/Comuki.Modules.Projects.Domain` — new enum +
  two new `ProjectSettings` fields + `Apply` overload.
- `platform/src/modules/Projects/Comuki.Modules.Projects.Application` —
  `IProjectDomainTypeResolver` port + `ProjectDomainTypeResolver`
  implementation, extended `ProjectSettingsView`, extended `ProjectMapper`,
  `UpdateSettingsCommand` / `UpdateSettingsHandler` /
  `UpdateSettingsValidator` extensions.
- `platform/src/modules/Projects/Comuki.Modules.Projects.Infrastructure` —
  EF configuration for the two columns, new migration
  (`AddProjectDomainRouting`), `ProjectsDatabase` table-name accessors if
  needed.
- `tests/unit/Comuki.Modules.Projects.Unit` — resolver unit tests
  (`ProjectDomainTypeResolverShould`), domain-defaults tests,
  mapper tests covering the new view fields.

No new modules. No new endpoints. No engine refs. No Host/Translator
touches. The migration ships through the existing `Comuki.Migrator` loop
(`Migrator.DatabaseSchemaEnsurer`).

## Non-goals

- Per-domain compute quotas, leases, budgets, or feature flags.
- Multi-domain routing in `RunLauncher` (planned, but not this slice —
  RunLauncher lives in `Comuki.Host` and is out of scope for slice 1).
- A new top-level `project_domains` table (would mean a new bounded context;
  deferred until RunLauncher needs it).
- Frontend wire-up (dashboard can read the new fields once the host exposes
  them — out of scope for slice 1).
- Real-domain-type classification in intake (chat/tracker) — slice 2.

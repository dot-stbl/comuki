## Purpose

Defines the open-core editions model: a closed `Community` tier (rank 0, no license required) plus one or more paid tiers identified by an open string code and an ordinal rank. Defines the capability registry as the single source of truth mapping every paid feature key and count quota to its minimum required tier rank, the signed-offline-key license format and its in-process Ed25519 verification, the four enforcement points (host API gating, module installers, background workers, dashboard / CLI feature visibility), the `edition.feature_unavailable` / `edition.limit_exceeded` 403 ProblemDetails shapes, the grace-period and read-only-degrade-on-expiry / downgrade behavior with the no-data-loss guarantee, the `/api/v1/edition` endpoint contract, and the three architecture-test invariants (registry ↔ attribute round-trip, every paid registry entry has a gate, Community-edition DI graph `ValidateOnBuild`s clean with zero paid services registered).

## ADDED Requirements

### Requirement: Open tier model with ordinal rank and open string code

The platform SHALL expose a `Community` tier (default, rank 0, no license required) and one or more paid tiers identified by an open string code and an ordinal rank. A paid tier SHALL be added by appending rows to the registry — never by editing a hardcoded enum or a closed list of SKU names. The tier code SHALL be stable across releases; the rank SHALL be the ordinal used by the capability registry to compare tier coverage.

#### Scenario: Community runs with no license

- **WHEN** the host boots with no `Host:License:Path` configured
- **THEN** `IEdition.Current` returns `Community` (rank 0), `IEdition.Status` returns `absent`, every endpoint, module installer, and background worker that requires a paid feature is gated accordingly, and the platform composes without errors

#### Scenario: Adding a third tier does not require a schema change

- **WHEN** a new paid tier is added by appending rows with a new code and `MinimumRank = 2`
- **THEN** the registry, license verifier, `/api/v1/edition` response, dashboard hook, and CLI helper all observe the new tier without a code or contract change to the editions capability

### Requirement: Capability registry as the single source of truth

A `Features` static catalog and a `Limits` static catalog SHALL together define every gated feature key and every count quota. Each entry SHALL carry a `Key` (dot.case, `resource:action` shape), a `Description`, and a `MinimumRank` (the smallest tier rank at which the feature is available). The registry SHALL be the single source of truth for every gate call site in the codebase; a feature that is gated anywhere but absent from the registry SHALL fail the build, and a registry entry that is paid (`MinimumRank > 0`) but gated nowhere SHALL fail the build.

#### Scenario: A typo in a gate call site fails the build

- **WHEN** a gate attribute references a `FeatureKey` string that does not exist in the registry
- **THEN** the architecture test `EditionsRegistryContainsEveryGateKeyShould` fails before the code can ship

#### Scenario: An unused paid entry fails the build

- **WHEN** a registry entry has `MinimumRank > 0` but no `[RequiresFeature]` / `[EnforceLimit]` / `[EditionFeature]` attribute references it
- **THEN** the architecture test `EveryPaidRegistryEntryIsGatedShould` fails before the code can ship

### Requirement: Generated Markdown capability table and TypeScript contract

The registry SHALL drive one generated Markdown table at `openspec/specs/editions/capability-matrix.md` (one row per entry; columns: `Key` / `Description` / `Community` / `Paid`) and one generated TypeScript module at `dashboard/src/shared/editions/_generated/registry.ts` (one `export const Features = { ... } as const` block and one `export type FeatureKey = (typeof Features)[keyof typeof Features]` union, with the parallel `Limits` pair). Both artifacts SHALL be generated by `tools/Comuki.Codegen.Editions` on every Debug build; a hand-edited copy SHALL NOT exist in the repository.

#### Scenario: Build regenerates both artifacts

- **WHEN** `dotnet build comuki.slnx -c Debug` runs after a registry change
- **THEN** the Markdown table and the TypeScript module are rewritten to match the new registry, byte-identically across Windows and Linux CI (line endings normalized to `\n`)

#### Scenario: Dashboard consumes the generated types

- **WHEN** the dashboard's `useFeature(Features.MultiRepo)` is compiled against the generated registry
- **THEN** the TypeScript compiler rejects a typo'd feature key at build time, mirroring the C# architecture test

### Requirement: Signed-offline license key with embedded public key

The license SHALL be a compact two-part token `base64url(payload-json).base64url(ed25519-signature)` where `payload-json` carries `org`, `edition` (tier code), `seats` / `limits` (open number map keyed by limit name), `expiry` (ISO-8601 UTC), `features` (explicit allowlist or implicit-by-rank — see "Two license modes" below), and a discriminator flag for the mode. The verifying public key SHALL be embedded in the binary as an assembly constant or `.resource`, never as configuration; a customer SHALL NOT be able to supply their own "public key" and self-sign. Verification SHALL be 100% offline: signature check against the embedded public key plus an expiry check against the local clock. **No network call SHALL ever be made as part of verification** — no phone-home, no telemetry exfiltration, no revocation check.

#### Scenario: Tampered token is rejected

- **WHEN** the signature on the license token does not verify against the embedded public key
- **THEN** `ILicenseProvider.Verify` throws `LicenseInvalidException`; the host logs the failure at startup and continues with `IEdition.Status = absent` (Community behavior); no network call is attempted

#### Scenario: Expired token is reported but does not crash boot

- **WHEN** the license token verifies but `expiry < now`
- **THEN** `IEdition.Status` returns `grace` (within `Host:License:GracePeriod`) or `expired` (past grace); the platform composes; read-only degrade applies (see "Grace period and read-only degrade" below); no network call is attempted

### Requirement: Two license modes — implicit-by-rank and explicit allowlist

A license SHALL declare, via a discriminator flag in its payload, which of two modes applies. The platform SHALL honor whichever the license declares and SHALL reject the other as a malformed license (`edition.feature_unavailable`).

#### Scenario: Implicit-by-rank is the default

- **WHEN** a license is signed with `mode: implicit-by-rank` and a tier rank of 1
- **THEN** the gate passes any registry entry with `MinimumRank ≤ 1` and refuses any entry with `MinimumRank > 1`, regardless of which feature keys the license payload names

#### Scenario: Explicit allowlist for enterprise deals

- **WHEN** a license is signed with `mode: explicit-allowlist` and a `features` list that includes `multi-repo` even though `multi-repo` requires rank 2 and the license's tier rank is 1
- **THEN** the gate passes `multi-repo` (the explicit allowlist overrides the rank) and refuses any other feature whose key is not in the allowlist (even if the rank would otherwise cover it)

### Requirement: License storage via TOML and secret reference, hot reload

`Host:License:Path` in `config.toml` SHALL hold a `SecretRef` value resolved through the existing `ISecretResolver` / `SecretRef` machinery (`env:` / `file:` / `vault:` / `consul:` schemes), so ops uses the same TOML / env / vault story as every other secret in this repo. The license SHALL be hot-reloadable: a replaced license file SHALL be picked up without restart, through `IOptionsMonitor<LicenseOptions>`. An absent `Host:License:Path` SHALL yield `IEdition.Status = absent` (Community behavior, no boot failure); a present-but-malformed license SHALL fail boot loudly per the "present-but-broken fails loud, absent behaves as Community" rule.

#### Scenario: Absent license behaves as Community

- **WHEN** `config.toml` does not set `Host:License:Path`
- **THEN** the host boots successfully with `IEdition.Current = Community`, `IEdition.Status = absent`, and the `/api/v1/edition` endpoint returns the Community view

#### Scenario: Replaced license is picked up without restart

- **WHEN** an operator replaces the license file referenced by `Host:License:Path` while the host is running
- **THEN** `IOptionsMonitor<LicenseOptions>` re-reads and re-verifies within `LicenseOptions.ReloadDelay` (default 5s); `IEdition.Current` and `IEdition.Status` reflect the new license on subsequent reads

### Requirement: Four enforcement points share one decision function

The platform SHALL enforce edition coverage at four points, all four required, each driven by declarative attribute / DI helpers, all calling one shared internal `EditionGate.EvaluateAsync` so the decision exists exactly once:

1. **Host API** — `[RequiresFeature(Feature)]` on MVC controllers / actions and `.RequireFeature(Feature)` on minimal-API `IEndpointConventionBuilder` extensions; evaluated by `RequiresFeatureFilter` (MVC) and `RequiresFeatureMiddleware` (minimal API), both reading the demand off the endpoint metadata with last-wins ordering.
2. **Module installers** — `AddComukiModule<TModule>()` reads a class-level `[EditionFeature(Feature)]` on `TModule` before invoking the module's concrete installer; a module whose feature is not covered is **logged at Warning naming the module and the missing feature key**, never silently no-op'd.
3. **Background workers** — `[RequiresFeature(Feature)]` on an `IComukiWorker` implementation (the hosted-service worker abstraction; not the ephemeral coding-agent worker) is checked by `ComukiWorkerRegistry` before the worker is registered; a gated worker is not added to the registry when the license does not cover it, rather than being added and having every `ExecuteAsync` early-return.
4. **Dashboard / CLI feature visibility** — `GET /api/v1/edition` returns the current tier, license status, and the visible feature keys so the UI / CLI can hide / upsell without hand-copying the registry.

#### Scenario: Paid endpoint denies a Community request

- **WHEN** an endpoint is tagged with `[RequiresFeature(Features.MultiRepo)]` and a Community-tier request arrives
- **THEN** the gate refuses with HTTP 403, `application/problem+json`, `code = edition.feature_unavailable`, `detail` naming the feature key and the minimum tier required

#### Scenario: Paid-tier module is skipped at boot when not covered

- **WHEN** a module is tagged with `[EditionFeature(Features.WhiteLabel)]` and the host boots under a Community (absent) license
- **THEN** `AddComukiModule<TModule>` logs a `Warning` naming the module and the missing feature key, does not invoke the module's installer, and the host continues to boot

#### Scenario: Gated worker is not registered under Community

- **WHEN** a worker is tagged with `[RequiresFeature(Features.BackgroundLlmWatchers)]` and the host boots under a Community (absent) license
- **THEN** `ComukiWorkerRegistry.Snapshot()` does not include the worker, no loop spins up for it, and the registry logs a `Warning` naming the worker and the missing feature key

### Requirement: `edition.feature_unavailable` and `edition.limit_exceeded` ProblemDetails

When a paid feature is invoked without a covering license, the platform SHALL answer HTTP 403 with `application/problem+json`, a stable dot.case `code` extension (`edition.feature_unavailable` for feature gates, `edition.limit_exceeded` for count-quota gates), a `detail` that names the feature key and the minimum edition required (never leaks license internals such as the embedded public key fingerprint, the signature, or the full payload), and a UI-facing extension carrying the feature key + minimum tier so the dashboard can render an upsell without a second call. The body SHALL be built with `TypedResults.Problem(...)` and routed through the existing `ProviderExceptionHandler` (`platform/src/host/Comuki.Host/Errors/ProviderExceptionHandler.cs:15`); controllers SHALL NOT hand-roll the body.

#### Scenario: ProblemDetails carries the minimum tier for upsell

- **WHEN** a Community request is denied by a `[RequiresFeature(Features.EnterpriseSso)]` gate
- **THEN** the response body is RFC 9457 problem+json with `code = edition.feature_unavailable` and the extension includes the feature key (`enterprise-sso`) and the minimum tier name (e.g. `team`), sufficient for the dashboard to render an upsell without a follow-up call

#### Scenario: Limit-exceeded shares the same shape with a sibling code

- **WHEN** a count-quota gate (`[EnforceLimit(Limits.Projects)]`) is checked against the current count and the call would exceed the cap
- **THEN** the response body is the same shape with `code = edition.limit_exceeded`, `detail` naming the limit key and the current count, and the extension carries the limit key + the cap

### Requirement: Grace period and read-only-degrade on expiry or downgrade

A `Host:License:GracePeriod` `TimeSpan` (default 14 days) SHALL control how long after `expiry` paid features keep working. While in grace, `IEdition.Status` returns `grace` and `/api/v1/edition` exposes `status: grace`; the gate still passes; a visible warning surfaces through `/api/v1/edition`. After grace, `IEdition.Status` becomes `expired` and the gate SHALL flip to **read-only degrade**: paid-gated *write* paths return `edition.feature_unavailable`; paid-gated *read / export* paths for data the customer already owns keep working, at minimum for export, so nothing is stranded. **No data SHALL be deleted by the gate; refusal to boot SHALL NEVER be the answer.**

#### Scenario: Grace period surfaces a warning without denying

- **WHEN** the license's `expiry` is within `Host:License:GracePeriod` of now
- **THEN** `IEdition.Status` returns `grace`, paid-feature gates still pass, and `/api/v1/edition` reports `status: grace` with a structured warning field

#### Scenario: Expired past grace denies writes but permits reads

- **WHEN** the license's `expiry` is past `Host:License:GracePeriod` of now and the tier's `MinimumRank` no longer covers a paid feature
- **THEN** paid-gated *write* endpoints return `edition.feature_unavailable`; paid-gated *read / export* endpoints for data the customer already owns still answer normally; no customer data is deleted by the gate

#### Scenario: Downgrade to Community does not strand existing projects

- **WHEN** a customer used `multi-project` under a paid tier and downgrades to Community
- **THEN** creating a *new* project returns `edition.feature_unavailable` (Community cap is 1); reading, listing, and exporting the customer's existing projects continue to work

### Requirement: `GET /api/v1/edition` endpoint

The host SHALL expose `GET /api/v1/edition` (anonymous; no permission required; route constant `ApiRoutes.Edition`) returning the current edition view for the dashboard and CLI. The response body SHALL be `{ tier: string, status: 'valid' | 'grace' | 'expired' | 'absent', features: { key: string, available: boolean }[], limits: { key: string, current: number, cap: number }[], version: string, expiresAt?: string }` where `version` is sourced from `ComukiBuildInformation` and `expiresAt` is the license's `expiry` (omitted when `Status = absent`). The endpoint SHALL be reachable without authentication so the dashboard's first paint can render an upsell before the user signs in.

#### Scenario: Community view reports available features and caps

- **WHEN** a client calls `GET /api/v1/edition` under a Community (absent) license
- **THEN** the response is 200 with `tier: 'community'`, `status: 'absent'`, the full feature set with `available` reflecting each entry's `MinimumRank ≤ 0`, the full limit set with `current` and `cap` reflecting the Community values, and `version` matching the host binary's `ComukiBuildInformation`

#### Scenario: Paid view reports covered features and includes expiry

- **WHEN** a client calls `GET /api/v1/edition` under a paid license with `expiry` in the future
- **THEN** the response is 200 with `tier: <paid code>`, `status: 'valid'`, the feature set with `available` reflecting the covered entries, and `expiresAt` carrying the ISO-8601 UTC expiry

### Requirement: Three architecture-test invariants

The platform SHALL enforce three invariants via `Comuki.Architecture.Tests` named `EditionsRegistryContainsEveryGateKeyShould`, `EveryPaidRegistryEntryIsGatedShould`, and `CommunityEditionComposesCleanlyShould`. The first walks every `[RequiresFeature]` / `[EnforceLimit]` / `[EditionFeature]` attribute across the compiled assemblies and asserts every key referenced exists in the registry; the second walks the registry and asserts every paid entry has at least one gate; the third extends `tests/unit/Comuki.Host.Unit.DiComposition/HostServiceProviderShould.cs:19` to build the full host service provider with a Community (absent) license and assert it validates with `ValidateOnBuild = true` and `ValidateScopes = true`.

#### Scenario: Community DI graph validates without a license

- **WHEN** `CommunityEditionComposesCleanlyShould` runs
- **THEN** it builds the host service provider with no license configured, force-enables `ValidateOnBuild` and `ValidateScopes`, and asserts the provider builds without a captive-dependency or missing-registration error — proving that Community composes with zero paid services registered, never crashing resolving one that assumed a license

#### Scenario: Adding a new paid feature without a gate fails the build

- **WHEN** a `Feature.Define(...)` row with `MinimumRank > 0` is added without a corresponding `[RequiresFeature]` / `[EnforceLimit]` / `[EditionFeature]` attribute anywhere in the codebase
- **THEN** `EveryPaidRegistryEntryIsGatedShould` fails the build with a message naming the orphaned feature key

#### Scenario: Adding a gate for a missing key fails the build

- **WHEN** a `[RequiresFeature]` attribute references a `FeatureKey` string that does not exist in the registry
- **THEN** `EditionsRegistryContainsEveryGateKeyShould` fails the build with a message naming the orphan gate and the missing key

### Requirement: Fixture licenses are test-only and never share keys with production

The test suite SHALL ship a `TestLicenseBuilder` that signs fixture licenses with a **test-only** Ed25519 keypair (never the production embedded public key). Two fixtures are required at minimum: `TestLicense.Community` (the absence fixture, asserting the platform composes with no license at all) and `TestLicense.With(Features.X)` (one paid-tier fixture covering at least one paid feature). The production embedded public key SHALL NOT appear in any test assembly or in any committed test fixture; the test-only keypair SHALL be regenerated on demand and SHALL be rotated independently of the production keypair.

#### Scenario: Tampered test fixture is rejected

- **WHEN** a test flips one byte of a `TestLicense.With(Features.X)` fixture
- **THEN** `Ed25519LicenseProvider.Verify` throws `LicenseInvalidException`; the test that depends on the fixture's tier observes `IEdition.Status = absent` and the gate denies

#### Scenario: Test-only keypair is independent of production

- **WHEN** the production embedded public key is rotated for a release
- **THEN** the test fixtures signed with the test-only keypair continue to verify without change, and the test-only keypair is never embedded in any production binary

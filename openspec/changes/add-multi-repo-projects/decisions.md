# Multi-repo / cross-product model — user decisions (grilling, 2026-09-25)

R1  Repository is a standalone registered unit (registry: url, host, credentials, policy). Projects ATTACH repositories (many-to-many) with a per-attachment role (primary/service/frontend/library/deploy-gitops/docs/...).
R2/R5 External block: when the needed change is in a repo where Comuki has no write (attachment access `external`), Comuki does NOT edit it. It sends a request via the repo's configured request channel (issue in their tracker if an integration exists / draft for a human to forward / PR from a fork if read access), with a spec of the needed capability written by the brain; our task goes `blocked-external`; an artifact watcher waits (version/tag/merge); the brain verifies the capability actually exists; then unblocks.
R3  Rules belong to the repository: protected branches, required checks, approvers, ONE merge queue per repository. The project only initiates work, pays budget, supplies memory/context.
R4  Credentials belong to the repository (one deploy token / GitHub App / GitLab integration per repo). Attachment has access level write|read|external; effective = min(attachment, credential). Optional per-attachment credential override is an exception.
R6  Links are repo→repo (global graph). Types: package/pin, submodule, api-contract, deploy/GitOps, codegen-consumer, read-context, fork/upstream. Each link type declares its handoff artifact (package version, commit SHA / submodule pointer, contract version, image tag, generated code, upstream merge). No separate ProjectLink — a cross-product link is a link between repos attached to different projects.
R7  Multi-project Mission: home project + participating projects. Work on repo R goes through the home project's write attachment if it has one (home budget/memory); otherwise the brain invites a participating project that has a write attachment (that project's approval via capability broker, its budget); if none → R5. Merge always follows R's rules (R3).
R8  One task = exactly one target repo (rw) + graph neighbours read-only as context (capped). A cross-repo change = several tasks in a DAG, one PR each. Submodule pointer bump is a mechanical step (no worker).
R9  Artifact readiness via source adapters (NuGet/npm feed, container registry, git tag, merge-to-branch, CI status) — webhook when available, else poll; each link has a version constraint (e.g. >= X). DAG merge: upstream merges → publishes artifact → downstream bumps pin → merges.
R10 Link auto-discovery on attach + periodic (.gitmodules, PackageReference/package.json, OpenAPI clients, helm/kustomize values, fork remotes) → `suggested`; only human-confirmed links drive planning/DAG; suggested are brain hints; drift (link vanished from manifests) → notification.
R11 Memory has two layers: repository layer (facts about the code/service/incidents; shared by all projects attaching the repo) + project layer (product architecture, infra, decisions). Background watchers observe the product (ns/dashboards/alerts); incidents map to repos via deploy links and are written to that repo's memory.
R12 Repo layer holds only facts derived from the repo itself and its incidents; project-originated context (tickets, customers, decisions) stays in the project; promotion project→repo only through redaction + provenance (like the epic's cross-project learning).
R13 Rollback: upstream changes must be backward compatible by default (contract check before merging upstream). If a downstream fails, its task goes back for rework; upstream untouched. Revert of upstream only if it broke other consumers — proposed automatically, merged on approval (revert-PR).
R14 New module Comuki.Modules.Repositories (registry, policies, links, discovery, artifact adapters, external requests). Projects holds attachments (project↔repo, role, access). Integrations (after #88) provides git-host/tracker connections and credentials.
R15 Epic amendment: #93 minimal-missions introduces HomeProject + MissionParticipation now (empty participants = single-project case); full participation mechanics (approval/budget) in add-multi-repo-projects; fix the "Mission belongs to exactly one Project" invariant in missions/spec.
R16 Brain visibility in project A: A's repos fully; graph neighbours' METADATA always (name, link type, artifact/version, public contract surface, owning projects) so it can detect "change needed there"; neighbours' code/memory only with read access of the initiator/attachment.
